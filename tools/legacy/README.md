# 旧 skill 的导出

这里的脚本从旧 skill 取出 `v1-final` 的代码来跑，把结果导出成 JSON，给新代码的测试做对照。脚本只用 Python 标准库，输出放在 `out/`。

| 脚本 | 输出 | 对照什么 |
| --- | --- | --- |
| `export_samples.py` | `out/samples.json` | 反例样本和旧构建校验的判定，见第一节 |
| `export_diff.py` | `out/diff-cases.json` | 文字的逐行对比，见第二节 |
| `export_writing.py` | `out/writing-cases.json` | 写作校验和回复自查，见第三节 |
| `export_reply_samples.py` | `out/reply-cases.json` | 旧模板复制出的回复文字，见第四节 |

公开版说明：`out/` 里来自公司内部项目的数据已经删去，其余数据里的项目名和内部名称换成了别的词。重跑脚本要用到原来那些项目的目录，公开版里重跑不了，只用现成的输出做对照。

## 一、反例样本

`export_samples.py` 把旧 skill 的反例样本导出成一份 JSON。新的校验拿它逐份对照，见「07 校验」第六节。

### 导出什么

旧的反例测试 `check-samples.py` 在一份合格的数据上各改一处，得到一百一十四份样本。每份样本导出以下内容：

- 样本的说明，就是 `check-samples.py` 里写的名字。
- 构建校验读到的页面数据，以及样本目录里的其他文件：队列文件、主线、落地记录。
- 预期的判定，以及旧构建校验实际给出的判定。
- 旧构建校验的每一条拦截和警告。
- 每条消息来自哪一道检查、哪一行代码。

### 怎么重跑

在仓库根目录运行：

```
python3 tools/legacy/export_samples.py
```

脚本用 git 从 `~/.agents/skills/product-loop` 取出标签 `v1-final` 的代码，解到临时目录再跑。旧 skill 的目录只读不写。旧 skill 放在别处时，用 `--skill` 指定目录。`--out` 可以改输出的位置。

脚本只用 Python 标准库。现在的输出用 Python 3.12 导出，跑一遍约半分钟。

### 核对

写文件之前，脚本做以下核对。有一项不过，就报错退出，不写文件。

1. 整份跑一遍旧的 `check-samples.py`。份数要和导出的相同，每份的预期、实际判定和第一行输出都要一致。
2. 每份样本带追踪再跑一遍。输出和退出码要和直接运行时逐字相同。
3. 追踪到的消息拼起来，要正好是旧构建校验的输出。
4. 用导出的数据重建每份样本，再跑一遍旧构建校验。输出要逐字不变。

重跑的结果逐字节相同。输出里没有时间，只在最外层记 `exported_from: v1-final`。

### 输出格式

输出是 `out/samples.json`。最外层的字段如下：

| 字段 | 内容 |
| --- | --- |
| `exported_from` | 标签名 `v1-final` |
| `commit` | 标签指向的提交 |
| `count` | 样本的份数 |
| `verdicts` | 判定的键和 `check-samples.py` 里的说法 |
| `base` | 各份样本共用的合格数据 |
| `checks` | 二十二道检查，每道命中的样本数和规则数 |
| `rules` | 旧代码里每一处产生消息的代码，以及命中它的样本数 |
| `samples` | 各份样本，顺序和 `check-samples.py` 相同 |

每份样本的字段如下：

| 字段 | 内容 |
| --- | --- |
| `id` | 稳定的编号，从 `legacy-001` 到 `legacy-114` |
| `name` | 样本的说明 |
| `source` | 样本在 `check-samples.py` 里的行号 |
| `code` | 构造样本的原代码 |
| `input` | 页面数据，也就是构建校验读到的 `round.json` |
| `files` | 页面数据旁边的文件，键是相对路径 |
| `expected` | 预期的判定 |
| `actual` | 旧构建校验实际的判定 |
| `match` | 预期和实际是否一致 |
| `messages` | 每一条拦截和警告 |
| `output` | 旧构建校验的退出码、标准输出和标准错误 |

判定取三个值：`block`、`warn`、`pass`。它们分别对应 `check-samples.py` 里的「拦住」「提醒」「放行」，也就是新设计里的拦截、警告、通过。

`files` 里的文件有两种写法：

- `{"json": 值}`：文件的内容是 `json.dumps(值, ensure_ascii=False)`。
- `{"text": 原文}`：文件的内容就是原文。坏掉的 JSON 和 Markdown 用这种写法。

没有队列文件的样本，`files` 里就没有 `队列.json`。

`messages` 的每一条有四个字段：

| 字段 | 内容 |
| --- | --- |
| `level` | `block` 或 `warn` |
| `text` | 消息的原文 |
| `check` | 来自二十二道检查的哪一道，例如 `check_cards` |
| `rule` | 产生消息的代码行，例如 `build-report.py:278`，行号以 `v1-final` 为准 |

`rules` 里的规则是旧代码里产生消息的代码行，不是新设计里的规则。每一条写明所在的函数、所属的检查、级别和该行的代码。

### 几点说明

- `input`、`base` 和 `files` 里的 JSON 保留原来的字段顺序，其余的键按名称排序。有一份样本的旧消息原样打印了一个字典，字段顺序一变，消息的原文就变了。
- 消息和输出里的临时目录换成了 `<样本目录>`。
- 旧构建校验遇到第一处拦截就停下，所以拦截的样本只有一处拦截。新的校验会收集全部问题，对照时看旧的拦截在不在新的结果里。
- 写作校验的拦截在旧输出里合成一段，开头一行是总的说明。导出时按行拆开，每行一条，总的说明只留在 `output` 里。
- 队列文件里的文字触发写作校验时，旧代码只给警告。所以 `rules` 里级别为 `block` 的规则，在 `messages` 里可能是 `warn`。
- `out/samples.json` 由脚本生成，不要手改，也不要交给格式化工具改写。

## 二、文字的逐行对比

`export_diff.py` 用旧的 `text_diff` 算一批改前改后，把输入和旧代码的输出一起导出。新代码是 `packages/model/src/text-diff.ts`，测试逐份对照。输出写成 JSON 以后，要和旧代码的逐字节相同。依据是「02 技术选型」第十八节。

### 导出什么

输入分三类。第一类是历史页面里的改前改后：

- 脚本在 `~/code`、`~/proj` 和 `~/Documents/doc/md/项目` 下找名为 `walk` 的文件夹。
- 读文件夹里的页面数据和生成的网页，取出每一处 `textBefore` 和 `textAfter`。网页里的数据取自 `report-data` 那一段。
- 这一次找到 32 个文件、82 处，去重后 41 对。它们来自四个项目的十六轮页面，每轮的页面数据和网页各一份，文字相同。
- 公开版删去了 8 对：7 对来自公司内部的项目；1 对的旧输出把换掉的名称拆进了逐字对比，没法照样替换。剩 33 对。

第二类是反例样本里的改前改后，取自 `out/samples.json`。共六处，去重后 2 对。有一处只给了改前，跳过。

第三类是构造的样例，共 468 份，公开版剩 454 份：

- 手写的边界情况 87 份。包括空文字、两边相同、只加行、只删行、回车换行、只改空白、很长的行、中文和表情。还包括改动之间隔的行数、改动在开头和末尾、空白行的保留、重复的行，以及 `context` 取 0、1、3、5。
- 由历史文字变出来的 81 份。每一对历史文字对调一次，再把改后的文字随机改几处。有一份改完和原文相同，跳过。公开版删去了由上面 8 对变出来的 14 份，剩 67 份。
- 随机生成的 300 份，种子固定为 17。字和行从很小的集合里取，重复的多，容易出现一样长的匹配。

相同的输入只留一份。历史页面里的一对文字出现在几处，就记下几处出处。

### 怎么重跑

在仓库根目录运行：

```
python3 tools/legacy/export_diff.py
```

取出旧代码的方法和 `export_samples.py` 相同，这一部分直接引用它。`--root` 改找历史页面的目录，可以写多次。找的时候跳过 `node_modules`、`.git`，以及产品循环自己的仓库和工作树。各项目的目录只读不写。

现在的输出用 Python 3.12 导出，跑一遍约五秒。历史页面不变时，重跑的结果逐字节相同。项目里多了新的页面，重跑会多出新的历史样例。

### 核对

写文件之前，脚本做以下核对。有一项不过，就报错退出，不写文件。

1. 每份输入只出现一次。手写的样例和前面的重复就报错，变出来的重复就跳过。
2. 输出写成 JSON 再读回来，和原来的完全相同，并且能写成 UTF-8。
3. 旧代码给每个 `SequenceMatcher` 都关掉了 autojunk。有两份手写的样例专门检验这一点，打开 autojunk 时结果必须改变。

### 输出格式

输出是 `out/diff-cases.json`。最外层的字段如下：

| 字段 | 内容 |
| --- | --- |
| `exported_from` | 标签名 `v1-final` |
| `commit` | 标签指向的提交 |
| `function` | `text_diff` 在旧代码里的位置 |
| `count` | 每一类的份数 |
| `cases` | 各份样例 |

每份样例的字段如下：

| 字段 | 内容 |
| --- | --- |
| `id` | 编号，例如 `history-007`、`edge-012` |
| `kind` | 类别：`history` 历史页面，`sample` 反例样本，`edge` 手写的边界情况，`derived` 由历史文字变出来的，`random` 随机生成的 |
| `sources` | 只有前两类有。每一处出处从项目的文件夹写起，后面是在数据里的位置 |
| `name` | 只有构造的样例有，写这一份检验什么 |
| `from` | 只有由历史文字变出来的样例有，写它来自哪一份历史样例 |
| `context` | 折叠时改动前后各留几行。只在不是默认的 2 时写 |
| `before`、`after` | 改前和改后的原文 |
| `output` | 旧 `text_diff` 的输出。每行是 `{k, parts}`，`parts` 里每一段写成 `[种类, 原文]` |

`output` 里一行写一行，其余照常缩进。文件由脚本生成，不要手改，也不要交给格式化工具改写。

### 照旧代码做的几处

新旧结果要逐字节相同，所以下面几处照旧代码做，有的看起来不合理：

- 两边相同时，结果只有一行 `gap`。
- 一边是空文字时，它算作一个空行。结果里会有一行删掉或加上的空行。
- 只去掉两头的换行符，回车留在行尾。同一段文字用回车换行和用换行写，每一行都显示成改过。
- 配对按删掉的行的顺序逐行决定，不回头调整。一行配上了靠后的一行，它前面还没配的行先作为加上的行排出。后面的删掉的行即使和那几行更像，也配不上了。
- 相似度要高于 0.3 才配对，正好 0.3 不配。一样像时取靠前的一行。
- 留下的范围后面紧跟的一行空白也留下。只看它前一行在不在范围里，所以最多多留一行。范围前面的空白不多留。
- 空白按 Python 的 `str.strip()` 算。和 JS 的 `trim()` 相比，多了 U+001C 到 U+001F 和 U+0085，少了 U+FEFF。
- 行内按码位比较，一个表情算一个字。

## 三、写作校验

`export_writing.py` 用旧的写作校验跑一批文字，把输入和旧代码的输出一起导出。新代码在 `packages/model/src/writing/`，测试逐条对照。两边不同的地方只能是「07 校验」第五节写明的有意改动，测试按样例编号列出每一处。

### 导出什么

文字分六类，份数是这一次导出的结果：

| 类别 | 来源 | 份数 |
| --- | --- | --- |
| `skill` | 旧正文 `SKILL.md`，按空行切成段 | 101 |
| `reference` | `references/` 下的九份参考文件，同样按段切。公开版删去其中两份（方法科普和一个真实项目的例子），剩七份 | 290 |
| `page` | 历史页面里旧构建校验会读的文字 | 4285 |
| `edge` | 手写的边界情况 | 92 |
| `selftest` | `check-reply.py` 自带的样本 | 12 |
| `reply` | 手写的回复 | 23 |

历史页面的文字按以下方法取：

- 找页面的目录和第二节相同，只收带 `stage` 字段的页面数据。walk 文件夹里的使用记录和量到的事实不是页面，不收。
- 取字的方法照旧构建校验。`check_writing` 读的区块跳过 `quote: true` 的原话。`wording_notes` 读的区块不跳过原话，另外多读设计规范。两处取到的字合在一起。
- 这一次在六个项目的 219 个文件里找到 26639 处文字，去重后 9614 份。公开版删去了公司内部项目的 29 个页面、3379 份文字，个人网站的 15 个页面、1944 份文字，以及换掉名称以后长度变了、和旧脚本对不上的 6 份，剩两个项目的 68 个页面、4285 份。

前四类跑两样旧代码：`writing.py` 的 `check`，以及 `build-report.py` 的措辞提醒 `wording_notes`。后两类跑 `check-reply.py` 的 `problems`。

另有 1146 个字符串只算长度和宽度，给新代码的两个度量函数做对照。它们是历史页面里对照表的行名和选项的每一格，以及手写样例里的每一句。公开版跟着删掉的页面去掉一部分，剩 366 个。

手写的边界情况检验旧代码的每一种消息，也检验 Python 和 JS 容易不同的地方，例如：

- 各种空白和断行：全角空格、0x1c 到 0x1f、0x85、行分隔符、字节顺序标记。
- 按码位计数和截取：表情算一个字，截取开头时不拆开。
- 全角数字和别的文字的数字，Python 的 `\d` 都认。
- 引号里的停用说法、引号里的长句和分号、没有配对的引号、链接后面紧跟的字。

### 怎么重跑

在仓库根目录运行：

```
python3 tools/legacy/export_writing.py
```

取出旧代码的方法和第一节相同，找历史页面的方法和第二节相同。这两部分直接引用那两个脚本。`--root` 改找历史页面的目录，可以写多次。各项目的目录只读不写。

现在的输出用 Python 3.12 导出，跑一遍约两秒。历史页面不变时，重跑的结果逐字节相同。项目里多了新的页面，重跑会多出新的样例，已有样例的编号不变。

### 核对

写文件之前，脚本做以下核对。有一项不过，就报错退出，不写文件。

1. 整份跑一遍旧的 `check-reply.py --selftest`，要全部通过。导出的十二条样本，判定要和样本写的预期相同。
2. 取页面文字的方法逐个区块和旧代码的 `walk_prose`、`walk_text` 比对，取到的字和顺序都要相同。
3. 措辞提醒都以「提醒：current 里」开头，条数和旧代码的 `WORDING` 命中的条数相同。
4. 手写的样例和自带的样本要覆盖旧代码的每一种消息。手写的样例不能和前面的文字重复，编号也不能重复。
5. 输出写成 JSON 再读回来，和原来的完全相同，并且能写成 UTF-8。

### 输出格式

输出是 `out/writing-cases.json`。最外层的字段如下：

| 字段 | 内容 |
| --- | --- |
| `exported_from` | 标签名 `v1-final` |
| `commit` | 标签指向的提交 |
| `functions` | 五个旧函数在代码里的位置 |
| `terms` | 旧代码的四张表：`banned`、`patterns`、`soft`，以及措辞一类的 `wording` |
| `count` | 每一类的份数 |
| `pages` | 样例的出处用到的历史页面，路径从项目的文件夹写起 |
| `measures` | 度量的字符串，每项写成 `[字符串, 长度, 宽度]` |
| `cases` | 各份样例 |

每份样例的字段如下：

| 字段 | 内容 |
| --- | --- |
| `id` | 编号，例如 `skill-013`、`edge-044`。历史页面的编号是 `page-` 加文字哈希的前十位 |
| `kind` | 类别，见上面的第一张表 |
| `source` | 旧正文、参考文件和自带的样本才有，写文件名和起始行号 |
| `page`、`where` | 历史页面才有。`page` 是在 `pages` 里的序号，`where` 是在数据里的位置 |
| `name` | 手写的样例才有，写这一份检验什么 |
| `want` | 自带的样本才有，写样本预期的判定 |
| `text` | 原文 |
| `block`、`warn` | 旧代码的拦截和警告，没有就不写 |
| `wording` | 前四类才有，措辞提醒去掉开头以后的原文，没有就不写 |
| `verdict` | 后两类才有，旧 `check-reply.py` 的判定，取 `block` 或 `pass` |

### 几点说明

- 措辞提醒的原文写着页面上的位置。导出时把文字放进 `current` 区块再跑，位置总是 `current`，所以去掉「提醒：current 里」这一段。
- 对照时，测试先把有意改动退回去再比。新的一边去掉引号连同里面的字，旧的一边把「露出来」的拦截换成警告。退回以后两边逐条相同。
- 历史页面的编号取哈希，不按顺序编。页面增加时，测试里按编号列出的样例不用重排。
- `out/writing-cases.json` 由脚本生成，不要手改，也不要交给格式化工具改写。

## 四、回复文字

`export_reply_samples.py` 用旧模板拼回复的代码生成一批回复文字，连同页面数据和点选一起导出。新代码是 `packages/model/src/legacy/reply-text.ts`，测试逐份对照。依据是第一期计划第 23 步。

### 导出什么

旧模板上「复制回复」的文字由 `templates/report/10-app.js` 的 `compose()` 拼出。它读网页上的这几样：

- 每张卡选的选项和写的备注。
- 场景清单和设计规范的三个按钮，以及修改时写的怎么改。
- 先对齐的两个按钮，以及用户自己的话。
- 队列看板上取消的事。
- 想法框，以及存下的图。

脚本在 Node 里按模板画出来的样子摆出这几样，原样运行 `compose()`，取出复制框里的文字。页面有两份：

| 页面 | 来源 | 内容 |
| --- | --- | --- |
| `sample` | 模板自带的 `sample.json`，看板上另加三件事 | 疑问、发现、提升、回到构思各有卡，阶段是改名以前的「修复」 |
| `think` | 在 `sample` 上改成构思第 3 轮 | 另加一张只有一个方向的卡，以及场景清单、设计规范和先对齐 |

看板上每件事的文字前面写 Q 编号，照第一期约定第 9 条。

### 输出格式

输出是 `out/reply-cases.json`。最外层的字段如下：

| 字段 | 内容 |
| --- | --- |
| `exported_from` | 标签名 `v1-final` |
| `commit` | 标签指向的提交 |
| `function` | `compose()` 在旧代码里的位置 |
| `sample` | 样例数据在旧代码里的路径 |
| `count` | 样本的份数 |
| `shapes` | 二十八种行，每种写编号、说明，以及出现在哪几份样本里 |
| `pages` | 两份页面数据，键是 `sample` 和 `think` |
| `cases` | 各份样本 |

每份样本的字段如下：

| 字段 | 内容 |
| --- | --- |
| `id` | 编号，从 `reply-001` 到 `reply-019` |
| `name` | 这一份检验什么 |
| `page` | 用哪一份页面 |
| `actions` | 用户的点选 |
| `text` | `compose()` 拼出的文字，也就是用户复制到的回复 |

`actions` 的字段如下，没点的不写：

| 字段 | 内容 |
| --- | --- |
| `cards` | 每张卡写 `key`，例如 `q1`、`f1`。`pick` 是选项的 key 或「否决」，`note` 是备注 |
| `scenes`、`spec` | `n` 是页面上的序号。`pick` 是保留、修改或删除，`edit` 是怎么改 |
| `align` | `n` 是页面上的序号。`pick` 是明白或不明白，`say` 是用户自己的话 |
| `queue` | 取消的事在看板上的文字，按点的先后 |
| `ideas` | 想法框里的文字 |
| `images` | 存下的图，每张写序号 `n` 和标识 `id` |

### 几点说明

- 图的标识是「图 n」这几个字的 SHA-256。后端存图也用 SHA-256，旧模板只写前六位。
- 图存下了，回复的文字里也还有它的标记，`compose()` 才把它写进最后一行。有一份样本存了四张图，删掉了一个标记，最后一行只有三张。
- 只有一个方向的卡，点那个方向时写选项的 key，例如「3a」。真实的回复里有更早的模板写的「同意」，新代码两种都认。
- 旧模板拼不出「不认可一条更改」。更改在旧模板上只给人看，没有按钮。
- 真实贴回的回复不由脚本导出。它们取自会话记录，放在 `packages/model/src/legacy/__fixtures__/real-replies.json`。
- `out/reply-cases.json` 由脚本生成，不要手改，也不要交给格式化工具改写。
