# 主线（产品循环 skill 自己的）

报告网页固定的链接：https://claude.ai/artifact/Qf62RoM9zxH8ZCthqC3D46 。每一轮发布到这一个链接；别的会话发布时把它作为要更新的地址传进去，并声明页面可以存图。每一轮的网页和数据留在 walk 文件夹里。

每一样后面写着是哪一轮定的。十样都已经点头，2026-09-20 离开构思。

## 一句话新闻稿（定位）

定（第 1 轮 1b）：产品循环是一个 Claude Code skill：让 AI 开发的软件变成别人能用的产品，五个阶段一个循环，人只点选项。它是 AI 协同人类开发的范式，现在还不够完善和系统。承诺：第一轮就拿到一份带改前改后图的报告。

## 给谁用

定（第 1 轮 2a）：一类，给人看的。用 AI 写软件的开发者，自己或同事都一样。现在怎么做：在项目上跑，每轮在网页上点选项贴回来。忍受：每轮要自己看一遍长网页。

## 要完成的任务

定（第 9 轮 1a）：四条，都是发生过的。
1. 把一个 AI 写的项目从到处小问题收敛到能交付。
2. 从整个产品看，决定下一步留什么、加什么、删什么。
3. 修改 skill 之前先看懂它为什么这样。情境：skill 某处让你不舒服。要完成的事：找到那条规矩的来源和理由，决定改还是留。现在凑合：在会话里一问一答，改完散在聊天记录里。忍受：同一件事问过两次。
4. 让 skill 本身的问题回到维护它的会话。情境：在别的项目里使用 skill 时，发现 skill 本身有问题。要完成的事：让问题回到维护 skill 的会话并得到处理。现在凑合：自己在两个会话之间转述。忍受：转述会走样，容易忘。

## 场景清单

定（第 9 轮 2a，第 10 轮 4a，第 11 轮 1a）：八个场景，按现在的模板写；第 15 轮、第 16 轮加了两个，一共十个。

### S1 回答疑问
1. 打开网页 → 页头写着系统、阶段、第几轮；五个阶段的进度；左边目录列出每一条，下面写着还剩几条没点。
2. 读第一条 → 左边依次是来源、待决定、选项、我的看法；来源一条一条的，右边有同名同号的图。
3. 点 a → 这个选项加粗边、打勾；目录里这一条打勾；还剩几条少一条。
4. 写备注 → 备注进复制结果。
5. 想到别的 → 底部的输入框随时能写，写得多会变高。
6. 点底部「还剩几条没点」 → 跳到第一条没点的。
7. 全部点完 → 点复制回复 → 得到几行：第一行是阶段和第几轮，下面每行以块的名字开头；贴回会话。

### S2 验收更改（这一页不用点）
1. 打开网页 → 目录里有更改这一组。
2. 点目录里的更改 → 跳到改前改后图，一对一对。
3. 点图 → 放大；再点关掉。
4. 不认可的 → 截一块贴进输入框并写一句，见场景「截图反馈」。

### S3 决定发现和提升
1. 读发现 → 左边是来源、哪里不舒服、选项；右边是截图或真组件，下面是问题出现的位置，写着场景和步骤的名字。
2. 真组件 → 可以悬停、点；下面的按钮切换条件。
3. 读提升 → 右边是中保真线稿、效果图或操作流程。
4. 点选项、复制、贴回，同「回答疑问」。

### S4 看使用阶段的结果（这一页不用点，第 8 轮 2a）
1. 打开使用阶段的那一页 → 每个场景一行：走通了，还是断在哪一步。
2. 断了的那一行 → 配着断的地方的截图。
3. 往下 → 覆盖表的缺口列在下面。

### S5 中途接手
1. 换一个人或换一次会话打开网页 → 页头的进度和「当前」说清做到哪里了。
2. 往下到队列那一块 → 看到还停着哪些事、各属于哪个阶段、谁提的。
3. 主线和决定两个文件 → 看得到每条为什么这样定。

### S6 skill 的问题反馈回来（第 8 轮 3a）
1. 你在项目的会话里同意反馈 → 那个会话把问题发给维护 skill 的会话。
2. 维护的会话 → 出现这条反馈和我的理解，这时 skill 还没有改。
3. 你决定什么时候改 → 不是现在就改的，进队列。
4. 到了那个阶段 → 你在页面上看到它。

### S7 截图反馈（第 10 轮 4a）
1. 在任何一个输入框里粘贴截图 → 立刻出现缩略图，光标的位置多出「〔图 1〕」。
2. 图还在存 → 复制按钮写着「正在存图」，点不了；存好之后变回「复制回复」。
3. 点缩略图 → 放大；再点关掉。
4. 点复制回复 → 最后一行是「图：」，每张图带标识的前六位。
5. 贴回会话 → AI 列出页面存的图，用前六位对出完整的那一个，读到图；回应里说明在图上看到了什么，没有读图不回应。
6. 存不了的时候 → 页面如实写出来，并提示把截图贴在会话里。

### S8 删改场景清单（第 11 轮 1a，只在构思阶段）
1. 打开构思阶段的那一页 → 场景清单单独一块；每个场景一条，步骤摊开成一串格子，上面做什么，下面该看到什么。
2. 点留 → 目录里这一条打勾，还剩几条少一条。
3. 点改 → 这一条下面出一个输入框，写怎么改。
4. 点删 → 这一条变灰。
5. 复制回复 → 每行写场景的名字；改的带上怎么改。

### S9 删改设计规范（第 15 轮 3a，只在构思阶段）
1. 打开构思阶段的那一页 → 设计规范是一面样张墙：颜色是色块，字号是真实大小的字，圆角和间距是真实大小的方块。
2. 点动效的样张 → 小方块按写的时长动一下。
3. 点留、改、删 → 左边那一项打勾；改的出输入框；删的变灰；还剩几条跟着少。
4. 复制回复 → 每行写这一格的名字；改的带上怎么改。

### S10 在窄屏上看（第 16 轮 3b）
1. 窄屏打开 → 没有左边一栏；所有的屏一条接一条往下排；顶上写还剩几条；回复粘在底部。
2. 点顶上的还剩几条 → 滑到第一条没点的。

第 15 轮、第 16 轮定了列表加详情之后，前面八个场景里的「目录」指左边的列表，「往下到」指点左边的那一项；步骤的意思没变，替人用的脚本按新的走法写。

五条判据：十个场景都过。「截图反馈」第 9 轮因为只有一步并进了「验收更改」，粘贴截图做出来之后有了自己的步骤，第 10 轮重新单独写。它的第 1 到 4 步脚本用替身走；第 5 步依赖发布的平台，每一版靠用户真贴一次。

面向 AI 的那一半（AI 读 skill 后在项目里执行）：
定（第 5 轮后的讨论）：不写场景。同一份正文换一个模型执行，结果完全不同，场景的前提不成立。
这一半里和模型无关的只有一样：生成网页前的那道脚本检查。不合规矩的页面生成不出来，并告诉 AI 哪一条不对。
找问题准不准、选项是不是真的两条路，取决于模型，由用户看报告判断，skill 不承诺。
要写的是一张边界表：每条规矩放在模板、脚本、正文三处的哪一处。先后：能交给模板的不交给脚本，能交给脚本的不写进正文。
边界表（定，第 6 轮）：
- 模板：编号只写数字；结果、理由、代价；块的顺序；页头和进度；我的看法两行（AI 只填选哪个、为什么两格）；一句一行（模板遇到句号自动换行）。
- 脚本，拦住：选项三句齐全；写了我看了什么；问题出现的位置写了名字；右边不放文字；证据的种类；队列每条写了阶段。
- 脚本，只提醒：措辞词表（红方、间隔号、口头说法、拿编号指代东西、统计数字）。
- 正文：五个阶段怎么走；三个根问题；怎么出选项；没看过的不写；不用比喻；写完整页从头读一遍；已发布的页面不再修改；会话里怎么回。

这个 skill 自己的使用阶段（定，第 7 轮 3b）：
- 面向人：脚本打开报告网页，按上面的场景走一遍，每步截图。
- 面向 AI：一组做偏的报告数据（每条规矩一份，含真实留下的）交给那道检查，记录被拦住、被提醒、漏过去的；一份合格的确认不会错拦。
- 更换模型或正文删减之后：固定的小样例项目，干净的会话从头执行一次，只和上一次对比，不进交付线。

不算场景：回看旧网页找当时为什么。想知道改没改，直接问 AI。

## 不做什么和胃口

不做：手机端、多人同时点、网页直接发回会话、网页内评论。
不做（第 7 轮 1a）：不按产品形态拆成几个 skill，不在正文里按形态适配。形态的差别放进参考文件，每种形态一份，只回答三件事：用什么替人用一遍；留下的记录长什么样；哪些东西和执行者无关、能够判定。
胃口：模板这一版两天改完，没改完的砍。
上一版到期（第 9 轮 3a）：砍掉属于提升的两件；使用、检查、修复各做一轮，这一版结束；这三轮里新冒出来的事只进队列，留给下一版。

上一版的胃口（提升第 1 轮）：一天，只做提升第 1 轮选中的三件，到期没做完的砍。做完之后不再自己开新的一版，等真实项目的反馈回来再开。

上一版要做的（提升第 1 轮选中的，写成任务，修复第 2、3 轮做完并验收）：
1. 验收更改，看改前改后这一步：文字的更改显示成逐行对比，删的涂红划线，加的涂绿。验收时看：同一处更改不用左右来回对。
2. 回答疑问，打开网页这一步：每个项目一个固定的链接，每一轮发布到同一个链接，文件夹里每轮留一份。验收时看：收藏的那个链接打开就是最新一轮。
3. 验收更改，不认可的截一块这一步：先试一次在页面上粘贴截图。验收时看：试的结果如实写出来，行还是不行。

这一版的胃口（构思第 10 轮 1a）：半天，只做 atlas design 那条反馈带出来的地方和构思第 10 轮选中的几件；改完出一页改前改后，这一版结束。之后照旧不自己开新的一版。

这一版要做的（构思第 10 轮选中的，写成任务；每一件同时在队列里记了一行。修复第 4 轮做完并验收，这一版结束）：
1. 中途接手，往下到队列那一块这一步：队列也收用户已经批准、还没做的事，每一行标要做它的那个阶段。验收时看：正文里队列的定义、提升怎么做的第 4 步、修复那一行三处说法一致。
2. skill 的问题反馈回来，到了那个阶段这一步：生成网页前的那道检查也读项目里的队列文件。验收时看：队列文件里有一行属于当前阶段、状态是等、页面里没有拿出来，页面生成不出来，并写明是哪一行。
3. 截图反馈：替人用的脚本加上这个场景，用替身走第 1 到 4 步。验收时看：使用阶段的那张表里多出这一行，并且走通。

这一版的胃口（构思第 13 轮 3b）：两到三天。报告网页重构：横向展开的骨架、设计规范自己的一块、新的表达形式一起做。到期没做完的砍。

## 交付线

定（第 7 轮 2a）：只写和模型无关、能用脚本验证的。
1. 规范化：不合规矩的报告数据，生成不出页面，并且说明哪一条不对。
2. 结构化：主线、决定、队列、每一轮的报告数据，都在固定的位置；缺了哪一样，脚本能报出来。
3. 清晰化：人打开报告网页，不询问 AI，就能点完所有选项并复制回复。

## 仓库和工程证据

这个仓库是自己的，不是和同事共用的。走查脚本和模板、正文一起提交；文档、决定、队列和每一轮的使用记录留在 `.product-loop/` 里，不提交。

落地必留的三样工程证据照通行的做法执行。另外三样在这里定：

- 依赖方向：查。规则是报告模板里不出现脚本的路径，脚本也不读模板里的状态。这一条用一次文本检索就能查出来。
- 重复和复杂度：不查。这个仓库只有脚本和模板两层，另装一套程序的代价大于收益，改由评审的子代理在意见里指出。
- 改了什么为什么：不另留。每一轮落地的计划和功能改动两份记录已经写明了这两件事。

## 四个风险

定（价值：第 3 轮用户原话；其余：第 8 轮 4a）：
- 价值：让 AI 模拟一个顶级的产品经理，找到项目里很多细节和人的精力注意不到的地方。
- 可用：风险是每一轮的页面太长，人看不下去。回答：一页只问当前阶段的事，右边只放看的东西，一句一行；用交付线里「不询问 AI 就能点完」来验证。
- 可行：模板和脚本做得出来，并且和模型无关；判断的质量取决于模型，不承诺。
- 商业：自己和同事使用，不出售。成本是用户每一轮花在页面上的时间，这个时间要比自己逐屏检查更省，这个 skill 才成立。以后想往页面里加东西，先过这一条。

## 常见问题与待定

- 报告网页右边要不要做成点标签切换的资源视图：已答。不做，右边只放看的东西，一样一块往下排。
- 选项三行的标签叫什么：已答。结果、理由、代价。
- 没有发现问题，是 skill 的缺陷还是模型能力：已答。判断能力够，是跳过了元素清单这一步；skill 的缺陷是跳过了没有人看得出来，所以元素清单变成必须留下的产物。
- 待定：无。

## 事前验尸

定（第 3 轮原因，第 4 轮 2a 对策）：
1. 原因：AI 的能力提升，不需要这个 skill 也能完整开发整个产品的流程。
   对策：重心放在人和 AI 之间的那一层，也就是报告网页、主线、决定、队列。教 AI 怎么思考的部分，每次更换模型删减一遍；删掉之后结果没有变差的，不再恢复。
2. 原因：skill 的内容劣化：大量不抽象的 if else 判断写满正文，核心的方法论和使用流程被掩盖甚至消失。
   对策：能用脚本检查的规矩写进脚本，正文只保留流程和方法。新增内容先抽象成类；正文每增加一段，先看能不能删除一段。

## 设计规范（报告网页的）

定（第 1 轮）：选项是小卡，选中加粗边加勾，结果、理由、代价三行分格；三行标签叫结果、理由、代价；构思的线稿放右边并排。
定（第 2 轮，后来被修复第 2 轮的反馈改过的已经按新的写）：
- 块的顺序：页头、要你点的（疑问、发现、提升、回到构思）、给你看的（更改）、队列、想法框；复制条常驻底部，写着还剩几条，带一个随时能写的输入框。
- 目录：宽屏左侧固定，每条一行，点过打勾；窄屏收成顶部「还剩几条」。
- 右边只放看的东西，直接展示，一样一块往下排；不放说明文字，不放要点开的按钮，不放文字摘录；没有可看的，这张卡一栏到底。
- 证据的形式和它证明的东西一样：尺寸画出来、颜色涂色块、字号排样张、间距画格子、截图裁片、组件用真组件。
- 问题出现的位置：一排场景格子、一排步骤点，场景和步骤都写名字。
- 疑问卡的 a、b 线稿放右边，各标字母。
- 编号只写数字；我的看法固定两行；选项三格是结果、理由、代价。

定（构思第 21 轮，六类都保留）：界面上的状态、字段、文案、小卡、参考的取值。每一类一张表，一行一条。

### 写作规范（决定 119 到 122）

适用于页面正文、会话回复、正文和参考文件。

**术语表**（左列停用）

| 停用的说法 | 统一的术语 | 含义 |
| --- | --- | --- |
| 替人用的脚本 | 走查脚本 | 按场景自动操作产品并截图的脚本 |
| 管落地的脚本 | 落地脚本 | 记录并校验落地五个步骤产出的脚本 |
| 生成网页前的那道检查 | 构建校验 | 生成报告页之前对页面数据做的校验 |
| 做偏的样例、样例检查 | 反例测试 | 故意写错的数据，用来验证校验能否拦住 |
| 改行为 | 功能改动 | 会改变产品行为的代码改动，与重构相对 |
| 整理 | 重构 | 不改变行为、只改善代码结构的改动 |
| 露、露出来 | 显示 | |
| 收起来、点开 | 折叠、展开 | |
| 那一格、那一块、那一屏 | 字段、区块、页面 | 写出名称，不用指示词代替 |
| 拦住、放行、提醒 | 拦截、通过、警告 | |
| 查……齐不齐 | 校验……是否齐全 | |
| 你定、问你 | 由用户决定、请用户确认 | 页面正文里用「用户」；会话里仍然称「你」 |

**句子**

- 每句有明确的主语。
- 句子不超过四十字，逗号隔开的每一段尽量在二十字以内。
- 指代明确，写出名称。
- 不用口语，不自造说法。

**段落和列表**：论证用段落，首句是主旨，一段三到五句，不超过七句；句子之间用关系词交代关系；三项以上的并列内容写成列表，列表前有一句引导语，各项语法结构一致；有先后用编号列表；多个对象在相同维度上比较时用表格，单元格不超过两句。

**需要避开的 AI 写作迹象**：三个一组的排比；「不是……而是……」式的对比；排比的短句连用；固定的开头套话。
