# 主线（产品循环自己的）

## 1 一句话新闻稿

AI 写软件快了，产品循环让开发者用五个阶段把软件改到能交付，改动附改前改后的图。

## 2 给谁用

- 用户：用 AI 写软件的开发者，只有自己一个人用。
- 什么时候用：AI 写完一个软件、要交给别人用之前。还有决定下一版加什么之前。
- 上一次：2026 年 9 月 29 日，在构思阶段的页上点选项。
- 现在怎么凑合：在项目上跑旧 skill。每个阶段在网页上点选项，再把回复复制贴回会话。
- 忍受什么：每个阶段都要复制粘贴一次。旧的记录散在各个项目的文件夹里，同时看几个项目时找不到哪个在等自己。

## 3 要完成的任务

每件写四样：要完成的事，情境，现在的凑合办法，忍受的成本。

1. 把一个 AI 写的项目收敛到能交付。
   - 情境：AI 写完一版软件，到处是小问题，用户要交给别人用。
   - 凑合：用户自己一屏一屏检查，发现一个问题就转告 AI 一次。
   - 成本：检查最花时间，漏看的问题要等别人用了才知道。
2. 从整个产品看，决定下一步留什么、加什么、删什么。
   - 情境：一版做完，用户要定下一版做什么。
   - 凑合：用户凭印象想，想到什么就让 AI 加什么。
   - 成本：功能只加不删，产品越加越乱，没有人问哪个该删。
3. 修改 skill 之前先看懂它为什么这样。
   - 情境：用户要改 skill 里的一条规矩。
   - 凑合：翻 skill 的正文和聊天记录，找这条规矩当初为什么定。
   - 成本：找不到来源就不敢改，改了又可能把当初的理由改丢。
4. 让 skill 本身的问题回到维护它的地方。
   - 情境：用户在别的项目里发现 skill 有问题。
   - 凑合：用户把问题从这个会话复制到维护 skill 的会话。
   - 成本：每次都要转述，转述会丢掉原始情况，同样的问题反复出现。
5. 同时照看几个项目。
   - 情境：用户手上有七个项目，各停在不同的阶段。
   - 凑合：逐个打开项目的文件夹和会话，看它停在哪。
   - 成本：找不到哪个项目有页在等，停了很多天也没有人发现。
6. 把软件装到电脑上，并保持能用。
   - 情境：换了电脑，或者拉了新版本，或者后端出了问题。
   - 凑合：照着仓库里的命令自己装，出了问题看日志。
   - 成本：装法写不清，装错了第一天就用不了。数据坏了没有办法恢复。
7. 把还用旧 skill 的项目迁过来。
   - 情境：项目里还留着旧 skill 的记录，迁移命令在 2026 年底删除。
   - 凑合：新旧两个 skill 并存，项目里有两套文件。
   - 成本：新命令用不了，旧记录一直散在项目里。

## 4 场景清单

每个场景写谁在什么时候用，为什么要做，做不成时谁会要求修。步骤写成「做什么 → 该看到什么」。
用户在工作台上看和点的是 S1 到 S12、S22 到 S25、S29、S33 和 S34。
AI 在会话里敲命令的是 S13 到 S21 和 S35。
安装、后端、升级、恢复、存储和整版的走法是 S26 到 S28、S30、S31、S36 和 S37，用户和 AI 一起做。
先对齐的词没看懂时，用户点了，AI 换讲法，是 S32，也是两个人一起做。

### S1 看所有项目停在哪

谁在什么时候用：用户，每天开工时，同时照看几个项目。要先处理在等自己的项目，不用逐个打开找。首页写错，用户会去错的项目，所以必须准。

1. 打开工作台首页 → 每个项目一行，写第几版、阶段、第几次和状态。还没开始阶段的写「第 2 版，还没开始阶段」。
2. 找有页在等用户的项目 → 排在最前，行上有「打开这一页」，按下直达那一页。别的按最近改动排，新的在前。
3. 看每个项目的队列 → 五个阶段各写有几件，零件写 0。停了七天以上的另写「停滞」。
4. 看到某个项目停在旧版 skill → 那一行写「旧版」和现在的版本号，行上不写命令。没迁移的写「未迁移」。
5. 备份有问题 → 首页和项目页顶上写一行，能关掉。这个浏览器里七天内不再出现，换浏览器还会出现。正在回复的页面上不出现。
6. 打开开发时用的验证页的地址 → 写「找不到这一页」，有页头和回到所有项目的入口。发布出去的工作台里没有验证页。

### S2 看一个项目走到哪了

谁在什么时候用：用户，想知道一个项目做到哪一步时。要定是等回复、接着做还是退回。进度画错，用户会重做已收尾的阶段，或者漏掉在等的页。

1. 点一个项目 → 进度按版本一行、阶段五列摆开。每个阶段一个方块，方块里有符号，不单靠颜色。
2. 悬停或聚焦一个方块 → 已收尾的写一句话小结，进行中的写「进行中」和开始日期。
3. 看「现在」这一块 → 当前阶段拿出来的事分三组：做完的、进行中的、要退回的。阶段没收尾，做完的也已分出来。
4. 点一个方块 → 进到那个阶段的页。页头和阶段条写现在的状态，标签页的标题写项目和阶段。
5. 打开已收尾且没有回复的那一页 → 选项点不了，没有输入框和提交，写着「阶段已收尾」。
6. 打开不存在的阶段或项目的地址 → 马上写「找不到这一页」。页头和回到上一级的入口都在。
7. 看「主线」和「决定」两块 → 主线块写现在是第几次修订，十个部分各一行，写了的打勾。决定块列最近几条，「全部」进决定页。
8. 项目有页在等回复，回到项目页 → 页头和「现在」里各有「打开这一页」，按下都到那一页。没有页在等时，两处都没有。

### S3 逐条点选项并提交

谁在什么时候用：用户，AI 给出一页等自己回复时。每一条定下来，AI 才能往下做。选项丢了或提交没送到，AI 会做错方向，用户得重点一遍。

1. 打开等我的那一页 → 页头写第几版、阶段、第几次。左边列出每一条，下面有「看未点的几条」。
2. 读一条 → 来源一条一条配图，选项按行对照。设计类的选项各有一张线稿。最后是我的看法和理由。
3. 点 a → 这个选项选中，左边这一条打勾，页面不自己走。「下一屏」只有页面底下这一个。
4. 按键盘右键 → 换到下一屏。光标在备注框里时，右键只移动光标。光标在选项上时，上下键换选项，左右键换屏。
5. 写备注，贴一张截图 → 截图立刻出现缩略图，文字里留下「〔图 1〕」。
6. 刷新页面，或者换一个浏览器打开 → 点过的选项、备注和截图都还在。
7. 收起左边一栏 → 提交、看未点的几条、想法框都还在。展开以后左边一栏回来，刷新后仍是收起的。
8. 点了要回复的几条，点提交 → 确认框写有几条回复、几条没点，和「提交后不能改」。确认后页面变成只读，提交区写「等 AI 取走」。

### S4 提交以后 AI 接着做

谁在什么时候用：用户，提交完回到对话时。不想再复制粘贴，也想知道 AI 有没有收到。提交后没人取走，用户会白等，所以要看得出来。

1. 提交，AI 正在等这一页 → 五秒内，提交区从「等 AI 取走」变成「AI 已收到」。没有 AI 在等时，一直写「等 AI 取走」。
2. 回到对话 → AI 已经在处理这一页的回复，不用复制粘贴。
3. 打开 AI 给出的下一页 → 顶上一块写着上一个阶段每一行去了哪里。去处是主线、决定、队列、当场做，或者不处理和原因。
4. 看这一页的想法框 → 是空的，上一页写的字没有带过来。
5. AI 撤回这一页，又给出一页 → 页头右边是两个页签，撤回的写「已撤回」，不靠划线。打开撤回的一页，提交区写状态，有原因才写原因。

### S5 验收更改

谁在什么时候用：用户，落地做完一批时。要确认改的东西真的改对了，这件事才算做完。认可的没改对，用户拿到手才发现，所以要看得清。

1. 打开落地的验收页 → 左边有「更改」一组。界面的更改是一对改前改后的图，文字的更改逐行对比。
2. 点图 → 放大，再点一下关掉。
3. 只看不点 → 看过的更改不会被记成认可，提交不能点。
4. 点了几条「认可」 → 左边这几条打勾，提交能点。没点的在确认框里写明还有几条。
5. 对一条改成「不认可」 → 要写一句为什么，没写时提交不能点，提示写原因。这一句进提交的内容。
6. 点提交 → 提交区写「AI 已收到」。认可的每一条在回复里是一行，不认可的一行带原因。
7. 看验收页左边的「工程证据」 → 写重构做了没有，和每件事先失败后通过。再写评审的意见或跳过的理由，和 AI 自己裁决的事。只看，不用点。

### S6 看使用阶段的结果

谁在什么时候用：用户，使用阶段跑完时。要知道产品有没有走通，哪一步断了。断处或截图对不上，用户会以为通过，所以要准。

1. 打开使用阶段的那一页 → 每个场景一行，写走通、断在第几步或没有走。走通的折叠，断了和没有走的展开步骤。
2. 看页的底部 → 没有想法框和提交，这一页不算在等的页。
3. 看断了的那一行 → 断处配一张截图，写着窗口宽度。
4. 往下看 → 覆盖表的缺口列在下面，每个缺口写页面、入口、操作或状态的名字。

### S7 删改场景清单

谁在什么时候用：用户，构思阶段定场景时。使用阶段要把场景逐个走一遍。删多了会漏测，留错了会白走。

1. 打开构思的那一页 → 场景清单单独一块，每个场景带编号，步骤摊开成一串格子。
2. 点保留 → 左边这一条打勾，未点的少一条。选中的「保留」是蓝色。
3. 点修改 → 这一条下面出现输入框，写怎么改。没写内容时提交不能点。
4. 点删除 → 这一条变灰，选中的「删除」是红色，文字仍写着。
5. 点提交 → 每个场景在回复里是一行，写场景的名字，和保留、修改或删除。

### S8 删改设计规范

谁在什么时候用：用户，构思阶段定外观时。检查阶段逐屏对着设计规范查，值不对就查不出对错。

1. 打开构思的那一页 → 设计规范是一面样张墙：色块、真实大小的字、真实大小的圆角和间距。每一项写着用在哪里。
2. 点一个动效的样张 → 小方块按样张上写的时长动一下，例如换一屏 220 毫秒。
3. 系统开了「减少动态效果」，再点动效的样张 → 小方块只变透明度，不位移。
4. 点保留、修改或删除 → 左边这一项打勾。修改的出输入框，删除的变灰。

### S9 看队列

谁在什么时候用：用户，想知道还有哪些事没做时。要定这个阶段做哪几件，哪几件不做了。看板和实际不一致，用户会漏做或重做。

1. 在项目页点队列 → 五列看板。等别的事的小卡放在五列上面，写明在等什么。有等待的那一列，列头写成「10，另有 1 件等待」。
2. 点一张小卡 → 出展示卡片，属性列阶段、状态、提出和加入时间，没有值的不列。有状态变化和出现在哪几个阶段。项目页上没有取消的按钮。
3. 看停了七天以上的 → 小卡的底和边变淡，字保持原色，写着「停滞」。
4. 在一个阶段的页里点「取消这一项」 → 要写原因，没写时提交不能点。这一句进提交的内容。

### S10 看主线和决定

谁在什么时候用：用户，想知道一件事为什么这样定时。找不到依据，用户会把已经定下的事再谈一遍。

1. 在项目页点主线 → 主线全文，右边是十个部分的目录。每个部分写最近一次改它的修订、日期和阶段。
2. 切到「原文比较」，选两次修订 → 按原文逐行对比。删的字红色划线，加的字绿色。
3. 切到「场景」 → 每个场景一块，写编号、名字、谁在什么时候用和步骤。
4. 点决定 → 一张表，最近的在最上面。默认只列有效的，作废的划掉，并写被哪一条推翻。
5. 搜一个词 → 只留下决定、原因或案例里有这个词的。搜不到时表头还在，写「没有找到」。
6. 点一条决定 → 卡片标题写这条决定的内容，改过文字的写改后的。卡片写它来自哪个阶段的哪一行回复。
7. 用键盘 Tab 到一条决定，按 Enter 或空格 → 停在这一条上时整行有框线，按下去打开展示卡片。Esc 关掉后键盘仍停在这一条上。
8. 打开一个还没有记过决定的项目，点决定 → 写「没有决定」，不摆只有表头的空表。

### S11 skill 的问题回到维护的地方

谁在什么时候用：用户，在别的项目里发现 skill 本身有问题时。问题要回到维护 skill 的地方，不用在两个会话之间转述。问题丢了，同样的规矩会一直坑别的项目。

1. 在那个项目的会话里，同意把问题报上去 → 会话用一条命令报上去，打印问题的编号。用户不用转述。
2. 打开 skill 的问题页 → 这一条在列表里，写项目、阶段、方面和类，状态是「新」。
3. 维护 skill 的会话回了理解 → 状态变成「已理解」，展开能看到原始情况和回复。卡片里只读，没有改状态的控件。
4. 用键盘 Tab 到一条问题，按 Enter → 整行有框线，按下去打开展示卡片。Esc 关掉后键盘仍停在这一行。
5. 往下看 → 后端算出三样信号：反复被拦截的规矩、停在旧版本的项目、停了很多天的事。点信号里的项目，进那个项目的页。

### S12 在窄屏上看

谁在什么时候用：用户，把浏览器放在半屏，一边看会话一边点页面时。窗口窄了，一页也要能点完。窄屏上点不了，用户只能换回全屏。

1. 把窗口拉到 1000 宽，打开一页在等的回复 → 没有左边一栏，所有的屏依次往下排。顶上有「看未点的几条」。
2. 点顶上的「看未点的几条」 → 滑到第一条还没点的，那一条贴在窗口顶上。
3. 系统开了「减少动态效果」，再点一次 → 直接到位，不平滑滚动。
4. 把窗口拉到 1100 宽 → 左边一栏回来，一次只摆一屏。

### S13 在一个项目里开工

谁在什么时候用：AI，用户要在一个项目里第一次用产品循环时。项目缓存和登记建不好，后面的命令找不到项目。第一步就卡住，用户会要求先修。

1. 在项目根目录敲 ploop init，不写 --repo → 退出码 2，写明先问用户仓库是自己的还是共用的。
2. 问过用户，敲 ploop init --repo 自己的 → 建好项目缓存。忽略规则写进 .gitignore，共用的写进 .git/info/exclude。
3. 后端还没开 → 命令自己启动后端，输出和后端开着时一样，不多打印一行。
4. 再敲 ploop → 写第 1 版、还没开始任何阶段、主线缺几个部分。下一步写着 ploop round start 构思。
5. 用户同意会话开始的钩子，敲 ploop init --hook 是 → 写进 .claude/settings.local.json。以后每次会话开始运行 ploop prime。
6. 再敲一次 ploop init → 写「已经开工过」，不重建，下一步写 ploop status。

### S14 会话中途接手

谁在什么时候用：AI，会话被压缩或换了一个会话时。要接着上一个会话做，不重来。接不上，AI 会重复开阶段或重复给出页，用户得重讲一遍。

1. 敲 ploop → 写当前第几版、哪个阶段、第几次，有没有一页在等，下一步敲什么。
2. 敲 ploop round show → 写这个阶段的状态、开始时间、拿出来的事和给出过的页。
3. 敲 ploop reply show → 列出最近一份回复的每一行，每行写卡片的标题和行的种类。
4. 上一个会话留下了没交上去的主线.md 改动，敲 ploop mainline pull → 被拦截，退出码 3。写明取回会丢掉这些改动，先交上去，或者加 --force。
5. 确定不要这些改动，敲 ploop mainline pull --force → 主线.md 换成最新的修订，写明没交的改动已丢掉。

### S15 开始一个阶段

谁在什么时候用：AI，进入一个阶段时。只拿这个阶段的事，不成立的事不带上页。不成立的事上了页，用户要白点一次。

1. 敲 ploop round start 检查 → 写「开始了：第 1 版的检查阶段」。逐件列出队列里检查的事，和这一版变过的屏。
2. 逐件看拿出来的事，不成立的敲 ploop queue drop → 必须写原因。这件事不上这个阶段的页，页上列在「取消的事」里。
3. 这件事要等别的事，敲 ploop round start 落地，加 --defer Q9=依赖 → Q9 变成等待，写着依赖。队列看板上它放在五列上面。
4. 同一个项目已有一个阶段开着时再开 → 退出码 3。写明开着的是哪个阶段、什么时候开的、怎么收尾。
5. 设计规范还缺部分时开检查阶段 → 退出码 1。写明缺几个部分，和怎么补。
6. 等的事等到了，取消的事要再做，敲 ploop queue reopen → 事项改回待办，编号不变。等待的事不再放在看板五列上面，回到它的阶段那一列。

### S16 给出信息

谁在什么时候用：AI，这个阶段的活做完、要给用户看时。页面数据不合规矩，用户会看到读不懂或点不完的页，所以交上去之前要拦。

1. 写好页面数据，敲 ploop page check → 不合格的每一条写明位置和怎么改，退出码 1。合格的写「通过」。
2. 敲 ploop page present → 截图上传，打印工作台里这一页的地址。
3. 已有一页在等用户时再给出 → 退出码 3，写明在等的是哪一页，和怎么撤回。
4. 敲 ploop page withdraw，写原因 → 这一页的页签写「已撤回」，可以再给出新的一页。

### S17 等回复并处理

谁在什么时候用：AI，给出一页以后。用户一提交就要接着做，不占用对话。回复丢了行，用户的选择就没有被处理。

1. 在后台敲 ploop reply wait → 命令挂着等，不占用对话。到时限还没人提交，退出码 7，再敲一次。
2. 用户在工作台点提交 → 命令退出码 0，打印回复的每一行。回复里的图已下载到项目缓存。
3. 敲 ploop reply handle，给每一行定去处 → 每行一个去处：主线、决定、队列、当场做，或不处理和原因。想法框里的话也是一行，由 AI 定去处。
4. 还有一行没定去处就给出下一页 → 退出码 1，列出没处理的行。开始下一个阶段也一样。
5. 用户在回复里改主意，推翻一条旧决定 → AI 敲 ploop decision add 记新的一条，再敲 ploop decision void 12 --by 15。决定页上旧的一条划掉，写被哪一条推翻。

### S18 落地一批

谁在什么时候用：AI，落地阶段。改代码要留证据，用户验收才有依据。不认可的事被记成完成，用户拿到手的就是没改好的。

1. 敲 ploop round start 落地 → 这一批要做的事逐件列出，中途冒出来的事只能进队列。
2. 落地时发现别的问题，敲 ploop queue add，写内容和 --stage → 打印新的编号，这件事不进这一批。内容超过四十个字被拦截，写明细节写进 --note。
3. 每件用 ploop land red 和 ploop land green 跑同一条命令 → 先记失败后记通过，两次的结果和提交号由命令记下。
4. 敲 ploop land review → 改动不超过六十行、三个文件时，可以加 --skip 写理由，命令核对后写明改了多少。超过时被拦截，要求评审。
5. 用户对一条更改点了不认可，AI 敲 ploop round close --done 这一件 → 被拦截。写明不认可的事不能算做完，要用 --return 退回。
6. 用 --return 写原因退回这一件，再敲 ploop round close → 这件事回到队列，收尾成功。
7. 有没提交的代码时敲 ploop round close → 被拒绝，列出没提交的文件。
8. 没给用户看过一页就收尾 → 被拦截，写明落地阶段收尾前要给用户看过至少一页。

### S19 跑使用代码

谁在什么时候用：AI，使用阶段。要像用户一样把产品每个场景用一遍，断点先修。没有截图，检查阶段就没有屏可看。

1. 敲 ploop use run → 逐个场景运行使用代码，走通，或者断在哪一步。每一步存两张截图，宽度是 1440 和 700。
2. 敲 ploop use coverage → 列出覆盖表的缺口。有缺口时退出码 1，覆盖表不存在时退出码 4。
3. 敲 ploop use changed → 按场景分组列出这一版新出现或变过的屏。
4. 给出使用阶段的那一页 → 使用区块由后端从这次运行生成，AI 不手写。这一页不等回复，直接收尾。

### S20 报 skill 的问题

谁在什么时候用：AI，用户同意把 skill 的问题报上去时。问题要回到维护 skill 的地方。只留在会话里，维护的人不知道。

1. 敲 ploop skill report，写方面和问题的类 → 打印问题的编号，工作台的 skill 问题页出现这一条。缺必填项时退出码 2，写明缺什么。
2. 维护 skill 的会话敲 ploop skill issues → 列出新报上来的问题，每条写哪个项目、哪个阶段。
3. 在产品循环自己的项目里敲 ploop skill issues reply，写理解 → 问题页上这一条的状态变成「已理解」。
4. 在别的项目里敲 ploop skill issues reply → 退出码 1，写明只有维护者能处理。别的项目只能用 ploop skill report 报问题。
5. 维护 skill 的会话敲 ploop skill issues set，改成已改，写 --fixed-in → 问题页上状态变成「已改」。卡片里写改在哪一版。不写 --fixed-in 时退出码 2，写明缺什么。

### S21 给旧项目体检

谁在什么时候用：AI，用户要迁移一个还用旧 skill 的项目时。项目停在旧版本，新命令用不了。迁移丢了数据，用户会要求马上修。

1. 在旧项目里敲任何一条命令 → 退出码 6，写项目停在旧版本，先敲 ploop doctor。
2. 敲 ploop doctor → 列出要迁移的内容，要判断的写进 .product-loop/migrate/。每处要确认的地方一行，以「确认：」开头。
3. 按「迁移的做法」改好 migrate/ 里的文件，再敲 ploop doctor → 不再列出要确认的地方。
4. 敲 ploop doctor --fix → 归档、导入、核对数量、写 project.json，最后清理旧文件。
5. 在工作台里打开迁移进来的旧网页 → 只写标题、日期和「旧页面无法显示」。没有内容的写「没有内容」，不显示旧页面的数据。
6. 已提交进 git 的旧文件 → 用 git 删除，单独提交一次，提交里只有这几个文件。再敲 ploop doctor 写「没有要迁移的地方」。
7. --fix 中途有一步失败 → 命令停下并列出原因，不清理旧文件。改好 migrate/ 后再敲 ploop doctor --fix，从停下的那一步接着做。
8. 迁移完成后敲 ploop → 写第 2 版，还没开始任何阶段。旧的阶段都在第 1 版。下一步写 ploop round start 构思。
9. 想退回旧 skill，敲 ploop export --legacy → 按旧格式写回主线、决定和队列，并写明把 skill 的链接改回旧正文。
10. 在工作台里打开迁移进来的、有内容的旧页面 → 内容照常显示，选项点不动。提交区写「这一页已回复」，没有提交按钮。

### S22 在半屏窗口上看各页

谁在什么时候用：用户，把浏览器放在半屏，一边看会话一边看各页时。七百到一千一百像素宽，页面不能破版。破了，用户只能换回全屏。

1. 把窗口拉到 700 宽，打开首页 → 每个项目一张卡，没有横向滚动条。
2. 打开项目页、队列、主线、决定、skill 的问题 → 都没有横向滚动条。页头的「目录」一栏和阶段条不拆字，长路径在值里折行。
3. 打开一页在等的回复 → 退回一张长页，没有左边一栏。选项多的卡摞成一个选项一张，没有横向滚动条。
4. 把窗口拉到 1024 宽，再打开项目页、队列、主线、决定、skill 的问题 → 都没有横向滚动条。
5. 打开同一页在等的回复 → 没有横向滚动条，提交在页面底下。

### S23 检查阶段逐条点发现的问题

谁在什么时候用：用户，AI 检查完一版，给出发现问题的页时。找问题是 AI 的活，用户只给每一条点一个选项。点不完或选项没被处理，检查就白做了。

1. 打开检查阶段的页 → 页头写第几版的检查阶段和状态。左边一栏列出每张发现问题的卡，一张一行。
2. 读一张卡 → 卡头写「发现问题」，和它属于必要性、认知一致性、交互一致性哪一类。下面依次是问题、来源和证据。
3. 看证据里的问题出现的位置 → 写场景的名字、这一步做什么、该看到什么，和第几步共几步。文字和主线里那一步一致。
4. 看选项 → 两到三个选项按行对照，共同的部分只写一遍。最后是我的看法和理由。
5. 点 a → 这个选项选中，左边这一张打勾，页面不自己走。
6. 在另一张卡上不点选项，只写备注 → 备注保存，提交时这一张是回复的一行。
7. 点提交 → 提交区写「等 AI 取走」。AI 敲 ploop reply wait，收到每张卡一行，写卡的标题和选的选项。
8. AI 敲 ploop reply handle → 选了要改的填「队列」，标落地。选了不改的填「不处理」，写原因。
9. AI 敲 ploop round start 落地 → 拿出来的事里有用户选中的那几件。

### S24 提升阶段逐条点提升的卡和线稿

谁在什么时候用：用户，落地做完一版，AI 站在整个产品上给出提升的页时。要定哪些功能留、加、删、重构、理清。没有线稿，用户看不到改完的样子，只能凭文字猜。

1. 打开提升阶段的页 → 左边一栏列出每张提升的卡。每张卡的标签写它是留、加、删、重构、理清里的哪一种。
2. 读一张卡 → 写它解决什么，补的是欠债还是加分。位置写在哪个场景的第几步，用户在这一步想做而做不了的是什么。
3. 看选项 → 两到三个选项按行对照。选项从删掉、合并、换成已有的机制、不改里来，不成立的方向不写。
4. 看卡右边的线稿 → 用项目里的真文字画出改完的样子，下面有一句说明。它不是截图。
5. 看另一张卡的操作流程 → 每步一句，画成一串带箭头的步骤。
6. 看只有一个方向的卡 → 写着只有这一个方向，下面列出排除的方向和原因。用户点同意或否决，也能在备注里点名捞回排除的方向。
7. 点 a，另一张点否决，点提交 → 提交区写「等 AI 取走」。
8. AI 先把选中的写进主线，再敲 ploop reply handle 填「队列」，写 --stage → 队列里记了一件。它标着要做它的阶段。
9. AI 敲 ploop round start 构思 → 写「开始了：第 2 版的构思阶段」。选中的那几件已在主线的场景清单里。

### S25 阶段开始时取消的事

谁在什么时候用：用户，AI 开始一个阶段并取消了几件不成立的事以后。取消要能被看见、被推翻。悄悄取消了要做的事，用户会漏掉它。

1. AI 敲 ploop round start 检查，再敲 ploop queue drop Q2，写原因 → 这件事变成已取消，不再上这个阶段的页。
2. 用户打开这个阶段的页 → 左边有「取消的事」一组。每件写内容和「取消的原因：…」。
3. 用户同意 → 这一组什么都不点，点完别的条再提交。回复里没有这一组的行，取消的事保持已取消。
4. 用户不同意一件 → 在这一组的备注里写这件事的名字和「还要做」，点提交。
5. AI 敲 ploop reply show → 有一行来自「取消的事」，内容是用户写的备注。
6. AI 敲 ploop reply handle，这一行填「队列」和那件事的编号 → 这件事回到待办，编号不变。状态说明写「用户在回复里点名捞回这件事」。
7. 用户打开项目的队列看板 → 这件事又在它的阶段那一列里。展开它，状态写待办。
8. AI 用 ploop reply handle 把一行指向早就取消的事 → 被拦截。写明要重新做就放进一件新的，来源写旧的编号。

### S26 第一次安装

谁在什么时候用：用户，在一台没装过产品循环的电脑上。要让 AI 能在自己的项目里用它。装法写不清或装错，用户第一天就用不了，所以要修。

1. 把仓库里 skill 文件夹里的内容复制到 ~/.claude/skills/product-loop → 那里有 SKILL.md 和 references。新开会话，技能里有 product-loop。
2. 在仓库根目录敲 pnpm install → 依赖装好，没有报错。Node 低于 24.12 时直接失败，写明版本要求。
3. 敲 pnpm ploop:setup → 写「装好了」、版本号、构建号、安装位置和命令的位置。~/.local/bin 不在 PATH 里时多一条警告，写明怎么加。
4. 新开一个终端，敲 ploop --version → 写版本号和构建号。
5. 敲 ploop open --all → 命令拉起后端，浏览器打开工作台首页，首页写「没有项目」。
6. 在项目根目录敲 ploop init --repo 自己的 → 写「开工了」，建好项目缓存，写好忽略规则。下一步写 ploop round start 构思。
7. 在项目里敲 ploop open → 浏览器打开这个项目的项目页，写「第 1 版，还没开始阶段」。刷新首页，多了这个项目一行。
8. 让 AI 敲 ploop round start 构思 → 写「开始了：第 1 版的构思阶段」，写出工作区和先做什么。

### S27 后端没开时

谁在什么时候用：AI 敲命令时，用户工作台开着时。后端是本机的进程，会退出。命令报错或页面丢内容，用户会当场要求修。

1. 后端没在运行，敲 ploop status → 命令自己拉起后端，输出和后端开着时一样，不多一行。
2. 敲 ploop backend status → 写在运行、进程、端口、工作台地址和构建号。
3. 工作台开着，敲 ploop backend stop → 几秒后页面顶上写「连不上，重连中」。提交区写「存不上」，不写英文码。
4. 连不上时在备注框里写几个字，再敲任一条 ploop 命令 → 命令拉起新的后端。十秒内页面恢复，顶上的提示消失，刚写的备注存下来。
5. 强行结束后端进程，再敲 ploop status → 命令照常拉起新的，输出和平时一样。
6. 后端的入口文件找不到，敲 ploop status → 退出码 5，写明怎么改：运行 ploop setup，重新安装这一版。
7. 敲 ploop backend logs → 打印最近的日志，写成中文。
8. 想自己启动后端，敲 ploop backend start → 后端没在运行就启动，写进程和端口。已在运行时再敲一次，写「后端已在运行」，进程不变。

### S28 升级到新版本

谁在什么时候用：用户，拉了新版本的代码以后。要用上新命令和新规则，又不丢旧项目的数据。升级后项目打不开或数据丢了，用户会要求马上修。

1. 在仓库里更新代码，敲 pnpm install 和 pnpm ploop:setup → 写「装好了」、新的版本号和构建号。版本号变了时，旧版本还留在 ~/.product-loop/app 下。
2. 敲 ploop --version → 写新的版本号和构建号。
3. 这一版改了数据库结构时，敲 ploop backup list → 列出升级前留的「迁移前」快照。
4. 在一个已有的项目里敲 ploop → 新后端被拉起。写的第几版、阶段和在等的页，和升级前一样。
5. 打开工作台 → 项目、页、决定和队列都还在，顶上没有连不上的提示。
6. 项目的 skill 版本第二段比这一版低时，敲 ploop → 多写一句「skill 有这个项目还没用上的新规则」。别的命令照常。
7. 项目的 skill 版本第一段比这一版低时，敲任一条改数据的命令 → 退出码 6。写项目停在旧版，先敲 ploop doctor。
8. 把仓库里 skill 文件夹里的内容再复制一遍到 ~/.claude/skills/product-loop → 里面的文件和仓库里的一致。
9. 新版装出问题，敲 ploop setup --version 旧版本号 → 切回已装过的版本，ploop --version 写旧版本号。

### S29 多个项目同时有页在等

谁在什么时候用：用户，两个项目的 AI 差不多同时给出页，回来一看都在等自己时。要按顺序处理，一个也不漏。顺序乱了或漏了，用户会让别的项目白等。

1. 两个项目各给出一页，打开首页 → 这两个项目排在最前，都写「等用户回复」。各有「打开这一页」，顶上写有几个项目有页在等。
2. 看这两个项目的先后 → 最近改动的排在前。改动时间相同时顺序固定，刷新不变。
3. 按第一个项目的「打开这一页」 → 到那个项目的那一页，页头写项目名、第几版和阶段。
4. 在那一页点完提交，回到首页 → 这个项目不再排在等回复的那一组，写「进行中」。另一个仍排在最前，顶上的个数少一个。
5. 另一个项目会话里的 ploop reply wait 加 --timeout 3 → 退出码 7，写还没有回复。只有提交的那个项目的命令被唤醒。
6. 同时有第三个项目给出使用阶段的页 → 那一行写「进行中」，有「打开这一页」。它排在等回复的项目后面，不计入有页在等。

### S30 出错以后恢复

谁在什么时候用：AI 和用户，命令或页面出错时。用户不知道怎么恢复，就得重点已经点过的选项，或者丢掉数据。出错后要能接着做。

1. 等回复的命令等到时限，用户还没提交 → 退出码 7，写还没有回复和等了多久。再敲一次同样的命令接着等。
2. 等的那一页被撤回，或被新的一页代替 → 退出码 8，写等的页已不在，下一步敲 ploop status。
3. 用户点提交时后端连不上，AI 随后敲任一条命令 → 页面不丢内容，也不写已提交。后端拉起后再点提交，成功，点过的选项都在。
4. 贴一张截图，图存不上 → 备注框下面写存不上的原因，能重试，文字里不留「〔图 1〕」。
5. 敲 ploop export → 在集中存储的 exports 下新建一个文件夹，里面有主线、决定、队列和每个阶段的文件。
6. 集中存储的数据坏了，敲 ploop backup list → 列出快照，每份写时间，都是北京时间。
7. 敲 ploop backup restore 快照名 → 只做预告：写会换成哪份快照，哪些项目会没有。没加 --yes 不恢复，退出码 1。
8. 问过用户，加 --yes 再敲 → 写「恢复了」。恢复前的数据库留成 pre-restore 快照，完整性检查写没有问题。
9. 恢复以后敲 ploop status → 快照以后才登记的项目退出码 6，写集中存储里没有登记它。敲 ploop init 重新登记，主线和各阶段的文件保留。
10. 想撤销这次恢复，敲 ploop backup restore，写 pre-restore 快照的名字，加 --yes → 回到恢复前的数据。

### S31 一版从构思走到提升

谁在什么时候用：用户和 AI，在一个项目里把一版从头走到尾时。循环本身就是这个产品，每个阶段的拦截和交接都要接得上。中间断了，这一版就收不了尾。

1. 在新项目里敲 ploop init --repo 自己的，再敲 ploop round start 构思 → 写「开始了：第 1 版的构思阶段」。同时写主线缺几个部分。
2. 补齐主线的十个部分，敲 ploop mainline push，给出构思的页，用户点完提交，AI 处理 → 回复的每一行有去处。
3. 主线还缺部分时敲 ploop round close → 被拦截，写明缺哪几个部分。补齐后收尾成功，下一步写开始使用。
4. 敲 ploop round start 使用，再敲 ploop use run → 使用代码逐个场景运行。有断点或覆盖缺口时，ploop round close 被拦截。
5. 修好断点，补齐缺口，给出使用阶段的页，敲 ploop round close → 页只给用户看，收尾成功。
6. 敲 ploop round start 检查 → 列出这一版变过的屏。检查页没盖住变过的屏时，ploop page present 被拦截，列出没盖住的屏。
7. 盖住以后给出检查的页，用户点完提交，AI 处理 → 选了要改的进队列，标落地。
8. 敲 ploop round start 落地，改完，给出验收页，用户认可每一条 → 每件做完，代码提交，ploop round close 成功。
9. 敲 ploop round start 提升，用户点完提交，AI 处理 → 选中的写进主线，队列里记了一件。
10. 敲 ploop round start 构思 → 写「开始了：第 2 版的构思阶段」。第 1 版结束，它的阶段都留在第 1 版。

### S32 先对齐的词没看懂

谁在什么时候用：用户，构思阶段的页上摆出新词时。词没看懂，要能说出来，让 AI 换一种讲法。只能点明白的话，用户会照着没懂的词定事，事后要求修。

1. 打开构思的页，看先对齐里的两张词卡 → 一个词一张卡：名称、用在哪张疑问卡、意思和例子。旁边有「明白」「不明白」和一个备注框。
2. 对一个词点「不明白」，用自己的话说一遍 → 「不明白」选中，左边这一项打勾。页面不自己走，写的话存下来，刷新后还在。
3. 一下删掉备注框里大半的字 → 框下面出现「找回刚删掉的文字」。按下，删掉的字回到框里。
4. 点另一个词的「明白」和疑问卡的 a，再点提交 → 确认框写几条回复和「提交后不能改」。确认后提交区写「等 AI 取走」。
5. AI 敲 ploop reply wait，再敲 ploop reply handle → 「不明白」那一行写词的名字和用户说的话。用到这个词的疑问卡定为不处理，写原因，不记进决定。
6. AI 写好下一页，词的意思和例子没改，敲 ploop page check → 通过，带一条警告。警告写用户点了不明白，讲法没变。点了明白的词不报。
7. AI 换一种讲法，敲 ploop page present → 给出了，没有这条警告。用户打开这一页，这个词的意思和例子是新的，备注框是空的。

### S33 读构思页上的参考和图表

谁在什么时候用：用户，构思阶段的页上，AI 查过外面的资料、画了图时。要看 AI 的建议凭什么，才敢定。资料写错或图画错，用户会照着错的依据定，事后要求修。

1. 打开构思的页，点左边的「参考」 → 每条参考一行，写名称、类型和建议。没有要点的选项，不算在没点的几条里。
2. 按一条参考 → 出展示卡片，写类型、阅读深度、相关度、证据强度、建议和用在哪里，下面是正文。Esc 关掉。
3. 参考多于八条 → 先摆八条，下面写「展开其余几条」。按下，其余的接着摆出来。
4. 读带图表的疑问卡 → 流程图画成图，目录树写成等宽的文字。每张图上写种类和标题。
5. 图表的文字定义写坏了，画不出来 → 这一张显示文字定义本身，不留空白。别的图照常。

### S34 工作台读数据慢或出错

谁在什么时候用：用户，打开工作台的页，本机服务答得慢或读不出来时。要知道是在读、读不出来，还是能再试一次。页面空白或者一直转，用户会以为工作台坏了。

1. 打开决定页，本机服务还没答 → 表的位置写「正在读取」。页头和四个页签已经在，没有空表。
2. 本机服务答了，说读不出来 → 换成「读不到决定。」，下面写原因，有「重试」。页头和页签还在。
3. 本机服务好了，按「重试」 → 重新读取，决定表出来。「读不到决定。」和「重试」都不见了。
4. 首页、队列、主线和 skill 的问题读不出来时 → 各写一句读不到什么，和原因，都有「重试」。按下能读回来。

### S35 写好的文字发出前自查

谁在什么时候用：AI，写要给用户看的文字，或者在会话里回复用户以前。文字不合写作规范，用户读着费劲，页面数据也会被拦。

1. 敲 ploop lint text，用管道传入一段文字 → 有拦截时退出码 1，写明哪里不对、怎么改和规矩名。只读，不写主线和队列。
2. 按报错改好，再查 → 写「查过了：没有拦截」，退出码 0。只有警告时退出码也是 0，警告写在下面。
3. 主线的「写作规范」一节加了停用的说法，再查 → 文字里有它就被拦截，写明要改成什么。
4. 敲 ploop lint reply，用管道传入要发的回复 → 有拦截时退出码 1。首行没写当前的阶段、写了文件名，或链接后面还有字，都拦截。
5. 改好再查 → 写「查过了：没有拦截」，退出码 0。

### S36 登录时自动启动后端

谁在什么时候用：用户，想一登录电脑后端就在，不想等第一条命令拉起它时。只有用户要才装。装错或卸不掉，登录项会一直留在系统里，所以要能装、能查、能卸。

1. 命令装好、后端开着，敲 ploop backend autostart status → 写「登录时自动启动后端：没装」，下一步写 ploop backend autostart on。装命令、开工和拉起后端，都没有装启动项。
2. 敲 ploop backend autostart on → 写「装好了」、启动项的位置和运行的命令。崩溃了会自动重启，ploop backend stop 停下后不再拉起。
3. 再敲 ploop backend autostart status → 写「已装」和「已加载：是」。
4. 敲 ploop backend autostart off → 写「卸掉了」，启动项文件删掉。下一条命令仍会拉起后端。

### S37 查看和清理集中存储

谁在什么时候用：用户，集中存储越来越大，想知道谁占了地方、清掉没用的附件时。误删有引用的附件，页面上的图会裂开。不清，占用只增不减。

1. 敲 ploop storage → 写附件的个数和大小、数据库的大小，按项目列出各自引用的附件。另写没有引用的附件个数和大小，和「超过七天的，ploop backup gc 会删除」。
2. 没有引用的附件才存下不到七天，敲 ploop backup gc → 写清理了 0 个附件。附件还在，没有引用的个数不变。
3. 那个附件存下超过七天，再敲 ploop backup gc → 写清理了几个附件、腾出多少字节。页面上引用着的图一张都没删。
4. 再敲 ploop storage → 没有引用的附件写 0 个。页面上的图还打得开。

## 5 不做什么和胃口

- 不做手机端。用户在电脑上用，常把浏览器放半屏，窗口最窄按 700 像素。
- 不做多人同时点。一个人用，同一时间只有一页在等用户点。
- 不做网页内评论。回复只走提交这一条路，AI 从一处取。
- 不做网页直接发回会话。回复由 AI 用命令取走，才能记下每一行的去处。
- 不做给别人卖。这是自己用的工具。
- 不做安装包和插件。用户选了复制 skill 目录、自己装命令的办法。
- 不做给不能敲命令的 AI 用的接口。用户用的 Claude Code 能敲命令，用不上。
- 不按产品形态拆成几个 skill。一个产品常同时有几种形态，只应该有一个循环，形态的差别放进参考文件。
- 不做深色配色。这一版只做浅色，颜色全走主题变量，以后补深色的取值。
- 胃口：这一版不设时间，做完为止。

## 6 交付线

用户拿到手的第一天，必须能做到下面几条。每条后面写用什么验证。

1. 装上：复制 skill 目录，装好命令，敲 ploop --version 有版本号。用 S26 验证。
2. 开工：在一个项目里敲 ploop init，接着 ploop 写出第几版和下一步。用 S13 验证。
3. 规范化：不合规矩的页面数据交不上去，报错写明哪一条不对、怎么改。用 S16 验证。
4. 结构化：主线、决定、队列和每个阶段的记录都在集中存储里，ploop export 能全部导出。缺了项目的登记，命令能报出来。用 S30 验证。
5. 清晰化：人打开一个阶段的页，不问 AI，就能点完选项并提交。用 S3、S23 和 S24 验证。
6. 可接手：换一个会话，敲 ploop 就知道做到哪里、下一步敲什么。用 S14 验证。
7. 改前改后：每处改动在验收页上有一对改前改后的图，文字的改动逐行对比。用 S5 验证。

## 7 四个风险

- 价值：风险是 AI 找到的问题，用户自己看一眼也能找到，产品就没有价值。对策是每张发现的卡都写位置和证据。度量是一个版本里，用户选了要改的发现有几条。
- 可用：风险是每个阶段的页面太长，用户看不下去。对策是一页只问当前阶段的事，右边只放看的东西。度量是每页从给出到提交的用时。
- 可行：风险是判断的质量取决于模型，软件保证不了。对策是只承诺和模型无关的部分：规范化、结构化、清晰化、可接手，都用测试和使用代码验证。
- 商业：自己使用，不出售。风险是每个阶段花在页面上的时间，比用户自己逐屏检查还多。对策是阶段收尾的小结里写页面用时，连续两个阶段更久就砍页面上的条数。

## 8 常见问题与待定

- 主线以哪份为准：git 里的 design/主线.md。改完交成新的修订，项目缓存里的那份跟着它。
- 旧的 skill 还能用吗：能。旧 skill 改名为 product-loop-bate，留给还没迁移的项目。迁移命令 ploop doctor 在 2026 年 12 月 31 日删除。
- 数据放在哪里：集中存储在家目录下的 .product-loop/，项目里只放项目缓存。数据库每天做一份快照，恢复的做法见 S30。
- skill 怎么给别人用：复制 skill 目录，自己装命令。步骤写在 README 里，场景见 S26。
- 后端要一直开着吗：不用。命令会自己拉起。想登录时自动启动，敲 ploop backend autostart on。
- 想法框里的话放去哪：它是回复的一行，和别的行一样，由 AI 定去处。
- 先对齐的「不明白」、参考和工程证据有场景吗：有。先对齐的「不明白」见 S32，参考见 S33，工程证据见 S5。
- 待定：深色配色的取值。问用户，第 2 版的提升阶段。
- 待定：价值和商业的度量怎么读。问用户，第 2 版的提升阶段。
- 待定：用户自己逐屏检查一个项目要多久，用来和页面用时比较。问用户，第 2 版的提升阶段。

## 9 事前验尸

1. 原因：AI 的能力提升，不需要这个软件也能走完产品的流程。
   对策：现在就把命令能查的规矩搬出正文。换模型时，删掉不带正文也做对的部分。
2. 原因：用户嫌每个阶段都要点页面，不再用。
   对策：现在就在每个阶段的收尾小结里写页面用时，连续两个阶段更久就砍条数。
3. 原因：正文、主线、使用代码和界面各写各的，越来越对不上，检查失去依据。
   对策：主线只留一份准本。使用阶段核对场景的步骤，对不上的报警告，当场改。

## 10 设计规范

### 信息结构

一个阶段一页。左边列出每一条，右边一次摆一屏，一屏有一到六条。
页头写第几版、阶段、第几次。下面是要用户点的，再下面是给用户看的，最下面是想法框和提交。
使用阶段的页只给用户看，没有想法框和提交，不算在等的页。
项目页有概览、队列、主线、决定四个页签。

### 配色

十个颜色，页面上不出现别的色：
- 白 #ffffff：页面、卡片、弹层。
- 浅底 #fafafa：左边一栏、表头、看板的列。
- 线 #ebebeb：所有边框和分隔线。
- 图标灰 #8d8d8d：图标和圆点，不用在字上。
- 次字 #5c5c5c：说明、属性值、时间。
- 墨 #171717：标题、正文、主按钮。
- 蓝 #0066db：选中、当前位置、链接、焦点框。
- 绿 #15803d：已完成、AI 已收到。
- 橙 #cb4600：等待、没收尾、出错。
- 红 #c62828：删除。

蓝只做字、圆点和框，不铺底。绿、橙、红只用在状态标签和原文比较的字上，面积很小。
选中分两类。选值用蓝框蓝字，例如保留、修改、明白、认可、选项卡，选中的删除用红框红字。
当前位置用蓝：左边一栏的当前行、阶段条的当前阶段、页签。
切换视图的分段控件不用蓝，选中的一段用深字加粗。

### 字体排版

西文用 Inter，中文用思源黑体，路径用 JetBrains Mono。
六档字号：标题 22 像素，小标题 18，正文 15，界面字 14，注 13，标签 12。
行高：标题 30，小标题 26，正文 26，界面字 22，注 20，标签 18。
标题和小标题字重 600，标签 500，其余 400。
句子不超过四十字。论证写成段落，并列的写成列表。字段名和标签用名词，两到四个字。

### 布局

列表加详情：左边一栏宽 288 像素固定，右边一次一屏。
1100 像素以下退回一张长页，没有左边一栏，所有的屏依次往下排。
最窄按 700 像素，不做手机端。700 到 1100 像素宽，各页没有横向滚动条。
间距用四像素的倍数，卡片里的块之间 24 像素，块内 8 像素。
圆角五档：4、6、8、10、14 像素。标签 6，按钮和输入框 8，卡片 10，弹层 14，小标记 4。

### 交互

点了选项，页面不自己走。换屏用页面底下的「下一屏」，同一屏上只有这一个。
键盘左右键换一屏，光标在备注框里时只移动光标。光标在选项上时，上下键换选项。
每个能点的东西都能用键盘点到，停在上面时有蓝色的焦点框。
点了要回复的就能提交，确认框写有几条回复、几条没点。
不认可、修改和取消要写原因或内容，没写时提交不能点。
提交以后页面只读，选项标为只读。

### 动效

用在六处：卡片换列、阶段推进、换一屏、选中的反馈、等 AI 取走时的圆点呼吸、悬停的颜色变化。
时长：卡片换列 360 毫秒，阶段推进 420，换一屏 220，选中的反馈 160，悬停 120。圆点呼吸两秒一次。
换一屏时新旧两屏同时过渡，总长 220 毫秒。取值写在主题文件里，由测试核对。
系统开了减少动态效果时：圆点不动，滚动直接到位，不位移，只保留透明度的变化。

### 图标和 SVG

图标用 Untitled UI 的图标库，线性，不用色块和字符代替。
用到的有：标志、折叠左边一栏、箭头、打勾、搜索、关闭，和阶段的四种符号。
阶段的四种符号是等用户回复、进行中、已收尾、未收尾，符号和颜色一起区分。
图标旁边有字，或者有读屏软件读的名字。图表由文字定义生成，不手画装饰性的图。

### 文案

界面上的字按写作规范写，书面语。称呼写「用户」和「AI」。
按钮以动词开头，写它做什么，例如「提交」「保存」「返回」「重试」「打开这一页」。
字段的值是短语，不成句，不带句号。区块名和标签是名字，不写成句子。
报错和空状态是提示，可以成句，不超过四十字。确认框写短语。
界面不解释自己：要靠一句说明才懂的控件，先改控件，不加说明。块的名字下面不加说明。
设计规范样张下面的「用在」是数据，不算说明，保留。
阶段的叫法只有一种，不用自造的简称。固定的名字「我的看法」指 AI 的看法，保留。时间一律写北京时间。
空状态写名字：没有项目、没有决定、没有找到。零件写 0。

### 给 AI 的界面

命令的输出第一行写结果，接着是要紧的几行，最后写下一步。
报错写明哪里不对、怎么改，加规矩名。加 --json 时输出机读的结果。
退出码：0 成功，1 拦截，2 用法错误，3 冲突，4 找不到。
5 是后端连不上，6 是要先做迁移检查，7 是还在等，8 是页已撤回。
命令的说明是二十字以内的名字。命令名用英文，输出用中文，和页面上叫同一个名字。

### 状态

队列的五种状态：待办、进行中、等待、已完成、已取消。
已完成要带完成证据，已取消要写原因，等待要写依赖。
停了七天以上的小卡写「停滞」，底和边变淡，字保持原色。
项目的状态：等用户回复、进行中、已收尾。页的状态：等 AI 取走、AI 已收到、这一页已回复、阶段已收尾、这一页已撤回。
读取中写「正在读取」，读不到写原因和「重试」，连不上写「连不上，重连中」。

### 无障碍

每个按钮都能用键盘点到，焦点框看得见。
颜色不单独表示意思：状态标签同时写字，阶段的方块带符号。
可点的东西不小于 24 像素见方。文字和背景的对比度不低于 4.5 比 1。

### 做法和阶段

构思的页有设计类的卡时，同一页要摆出用到的规范，缺了会被拦截。
设计类的卡先看外面的设计，再画线稿，再谈。
检查阶段逐屏对着这一节查。进入检查以前，这十二样要写齐，命令会查。
