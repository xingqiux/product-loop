# 维护说明

本文写维护这个软件和 skill 时要守的规矩，只有维护的会话读，见「09 skill 与软件」第一节。

## 一、校验规则

校验分三层：数据定义、校验规则和写作校验，见「07 校验」第一节。本节写后两层的规则怎么加、怎么删。写作校验的每一项也登记成一条规则。

共用定义里的规则只看数据本身，浏览器和后端都能跑。要查数据库的规则放在后端的内核里，写法相同。

### 加一条规则

加一条规则要一起交四样：规则本身、文案表里的报错、样本和规则表里的一行。缺一样，总测试就失败。步骤如下：

1. 定编号。编号写成两段或三段，用点隔开。每段是英文小驼峰，以小写字母开头，只用字母和数字。第一段写领域，也就是规则查的对象，如 `writing`、`decision`、`queue`、`land`。例子是 `decision.fields`、`land.oneCommit` 和 `writing.sentence.tooLong`。设计文档里带短横的编号，一律改成小驼峰。编号定了就不改，拦截和警告的记录按编号统计。
2. 写规则。用 `defineRule` 写成一个对象，写明级别、范围、起始日期、需要的上下文、检查函数、文案和样本。页面数据的规则放在 `packages/model/src/rules/` 下。一个文件放一条规则，或者同一个领域的几条。
3. 写检查函数。检查函数只返回命中的位置和参数，不写报错的文字。它一次返回全部命中，不在第一处停下。共用定义里的规则不查数据库，要的东西在 `needs` 里声明，由调用的一方传进来。
4. 写文案。报错放进 `packages/model/src/copy/` 下这个领域的文案：`message` 写什么不对，`hint` 写怎么改。查什么和依据写进 `copy/rules.ts` 的 `about`，键和编号相同。依据写这条规则来自哪一条决定、哪一次事故，或者设计文档的哪一节。
5. 定起始日期。从旧脚本搬过来的检查，取它加进旧脚本的日期。做法是在子树导入的提交历史里用 `git log -S` 查报错的那一行，再人工核对，见约定 0001 第 14 条。导入的提交里，旧脚本用的是原来的路径，例如 `scripts/build-report.py`，不在 `skill/` 下。限定路径时要加 `--full-history`，例如 `git log --full-history -S'usedIn' -- scripts/build-report.py`，否则查不到。新规则写 `sinceRelease`，指 2.0.0 发布那天。
6. 写样本。样本放在同名的 `.samples.ts` 里，包括一份基础数据和至少一份会命中的样本。规则在基础数据上不能命中。会命中的样本在基础数据上改一处，写明预期的位置和参数。
7. 登记。把规则加进 `packages/model/src/rules/registry.ts` 的 `defineRules`。再运行 `pnpm --filter @product-loop/model rules-doc`，重新生成下面的规则表。编号列在「已定编号」那张表里的，同时从 `pendingRules` 里删掉。

要查数据库的规则放在后端。它的说明写进 `packages/model/src/rules/backend.ts`，检查、报错和样本放在 `packages/backend/src/core/rules/` 下，登记进那里的 `backendRuleList`。检查写在用例里的，例如队列的状态图，只在 `backend.ts` 登记说明，写明检查在哪里。后端的总测试核对两边对得上。

总测试逐条查以下几项：

- 编号的写法对，不和别的规则重复，也不和已定编号的重复。
- 级别、范围、起始日期和需要的上下文写得对。
- 报错、查什么和依据都在文案表里，写作校验没有拦截。
- 在基础数据上不命中。
- 每份会命中的样本，位置和参数都和预期相同，报错里的参数都填上了。
- 规则表里有这一行，和程序生成的逐字相同。

### 执行规则

`runRules` 执行一组规则，每条都跑完，把全部命中收齐再返回。结果分拦截和警告两组，每条写规矩的编号、什么不对、怎么改和在哪里。顺序先按传进来的规则，同一条规则按检查函数给出的顺序。

迁移旧页面时用历史页面模式，并写明页面的日期，见「07 校验」第七节。起始日期不早于页面日期的规则跳过：起始日期只精确到天，同一天生成的页面可能早于规则。起始写 2.0.0 的规则，在 2.0.0 发布以前对任何旧页面都跳过。发布那天，在 `packages/model/src/rules/rule.ts` 的 `releaseDay` 填上日期。

只在某些阶段查的规则，执行时要写明阶段，别的阶段不执行。

### 删一条规则

删一条规则也要写明依据，见「07 校验」第八节。skill 的问题页上，某条规则长期没有命中，说明它可能已经没用。某条规则反复命中，又集中在少数几种写法上，说明报错的「怎么改」可能没写清。两种情况都由维护者判断，不自动删改。

## 三、打包和测试

`pnpm build` 运行 `scripts/build.ts`，用 tsdown 把后端和命令行打进 `dist/app/`，再用 Vite 把工作台打进 `dist/app/web/`。
目录里有 `ploop.mjs`、`backend.mjs`、原生文件、`drizzle/`、`web/` 和 `build.json`。
构建号由命令行的版本、提交短号和构建时间组成，两个入口打进同一个值。

`pnpm use` 先把运行目录打进临时目录，见 `scripts/use-setup.ts`。
命令的使用测试运行打包的 `ploop.mjs`，它再拉起旁边的 `backend.mjs`。
单独跑一个测试文件时没有这一步，沙盒直接运行源码。

`open.use.test.ts` 用 playwright-core 开一个无头浏览器，在工作台里写想法、贴图、提交。
它先用本机的 Chrome，没有就用 Playwright 下载过的 Chromium。两样都没有时这个测试失败。
playwright-core 不下载浏览器，要用 Chromium 时运行 `pnpm exec playwright-core install chromium`。

这个软件自己的使用代码在 `scripts/use/`，由 `use-code.use.test.ts` 整个跑一遍，主线的 S1 到 S37 一个不落。
场景分三类，各类有哪些编号，见 `design/主线.md` 的场景清单开头。
人的场景用同一个浏览器在工作台里点，见 `browser.ts`，要摆的页面在 `pages.ts`。
AI 的场景只敲命令。
安装、后端、升级、恢复和整版的场景，用户和 AI 一起做，命令和浏览器两样都用。
安装和升级的场景都在临时的 HOME 和 PLOOP_HOME 里做，不写真实的 `~/.local/bin`、`~/.product-loop` 和 `~/.claude`。
登录启动项的场景（S36）把 launchctl 换成只记参数的假脚本（环境变量 `PLOOP_LAUNCHCTL`），启动项写进临时家目录下的 `Library/LaunchAgents`，不碰真实的 launchd 和 `~/Library/LaunchAgents`。
清理存储的场景（S37）要造出存下超过七天的附件，只在临时的集中存储里直接改库里附件的存入时间。

场景的每一步和 `design/主线.md` 逐字对齐：步数、每步的 do 和 expect 一字不差，句末的句号也要。
运行器（`mainline.ts`）核对，对不上就打印「对不上主线」并以退出码 1 结束，当场改代码，不改主线迁就。
主线加了一个场景或一步，`use-code.use.test.ts` 的场景编号也要跟着改。

每一步走完，运行器给有窗口的步骤按 1440 和 700 两个宽度各截一张，存进 `screens/`，
步号相同、宽度不同，各写一项。要看窄屏或半屏的步骤，另在自己的宽度再截一张。
命令行的场景没有屏，不编截图：每一步敲过的命令、退出码和输出的开头记进这一步的 facts。
一步走不通时，断处也截一张，写明窗口宽度。

覆盖表是 `scripts/use/覆盖表.md`：产品里的页面、入口、操作、状态、命令和交接处，每行写被哪个场景用到。
`ploop use coverage` 列出没有场景的行。加了页面、入口、操作、状态或命令，同时加一行。

改了一个场景，可以只跑它：先 `node scripts/build.ts <目录>` 打出运行目录，
再 `PLOOP_TEST_APP=<目录> PLOOP_USE_OUT=<目录2> node scripts/use/run.ts S3`。结果写进 `PLOOP_USE_OUT` 下的 `use-run.json`。
改了工作台或后端，要重新打运行目录。

用命令走一遍使用阶段，也在沙盒里做：临时 HOME 和 PLOOP_HOME、端口写 0，项目根目录里放一个指向本仓库 `scripts/` 的链接，
项目缓存里放 `design/主线.md` 的一份，`ploop mainline push` 交上去，走到使用阶段，再敲
`ploop use run -- node scripts/use/run.ts`。它对照最新的主线核对每一步，没有断点也没有缺口时自动给出使用阶段的页。

`pnpm perf` 运行 `scripts/perf/round-page.ts`，量一个阶段的页面打开要多久，见第二期计划第 23 步。
它自己把运行目录打进临时文件夹，在隔离的沙盒里摆出检查阶段的一页：三十张卡（疑问和发现问题各半，都带
选项和来源）、一百张图，敲 `ploop page present`，再用无头 Chrome 分别以宽屏（1440）和窄屏（700）两种
视口打开这一页。量的是从这一页的 navigation start 到「能用」的毫秒数：宽屏看左边一栏的每一条和第一屏
是不是都出现，窄屏没有侧栏、所有屏一次铺开，看是不是都出现。各测五次取中位数，中位数超过一千毫秒退出码
写 1，量的正是「一页有三十张卡、一百张图时，本机打开不超过一秒」这条验收。结束时关掉自己拉起的后端、
删掉临时目录。
