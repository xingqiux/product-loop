# 形态：由模型执行的产品

产品是一段给模型读的文字时，读这一份。skill、提示词、给 agent 的说明都算。五个阶段、主线、三个根问题和工作台上的页面都不变，变的只有下面三件事。

先说前提：同一份文字换一个模型执行，结果完全不同。结果不好时，分不清是文字写得不好，还是模型能力不够。所以这种形态不写「模型读完之后应该怎么做」的场景，也不承诺模型判断得准不准。

## 一、替人用一遍的办法

这种产品通常有两面。

- 面向人的一面：它给人看的页面、文件、回复。这是普通产品，按界面或命令行那一份来用。
- 面向模型的一面：用的不是模型，是产物出门前的校验。

校验的用法是这样：

1. 准备一组做偏的产物，每条规矩一份。真实留下过的偏差优先收进来。
2. 交给校验，看它拦截了哪些，漏过了哪些。
3. 再准备一份合格的，确认不会被错拦。

产品循环自己的例子是仓库里的样本。每条规则都有一份基础数据和至少一份会命中的样本，预期的判定写在样本里。

更换模型，或者文字删减之后，另外做一次对比。用一个固定的小样例项目，开一个没有任何上下文的会话，从头执行一次。把留下的产物和上一次对比。这一次不算通过或不通过。

## 二、留下的记录

每个样本一行：应该被拦截、被警告还是通过，实际怎样。漏过去的和错拦的就是断点。给用户看时画成一张表，补之前和补之后并排。

## 三、可判定的东西

规矩放在五处，有先后。前面能做的，不放到后面：

1. 数据定义：固定的字段、格式、取值。写死以后，模型没有机会写错。
2. 校验规则，拦截：结构一类。该填的有没有填，该留的产物有没有留。
3. 校验规则，警告：措辞一类。要看上下文，可能是正当的引用。
4. 命令：流程的步骤、状态和读写。
5. 正文：前面都做不了的，也就是怎么看、怎么判断。这一部分取决于模型，由人看页面判断。

新规矩先问能不能放进数据定义，再问能不能放进校验或命令。都不能，才写进正文。
