# 提升的做法

前四个阶段只把已有的东西做对，不会生出新东西，也不会主动删东西。提升单独是一个阶段。它站在整个产品上，把功能一个个过。每个功能问：留、加、删、重构，还是理清。

检查不一样。检查站在现在的样子上，沿着修的路找哪里不对、哪里不舒服。

## 一、进入的时机

- 落地做完，按循环走到提升阶段。
- 用户说需要提升，或者说把整个产品过一遍。
- 用户的想法：想法先进队列，阶段标提升，由你用 `ploop reply handle` 放进去，不直接做。进入提升阶段时，从队列里拿出来。

提升只在提升阶段出卡。别的阶段不带提升卡。落地时自己挑出的问题，直接进队列，不出提升卡。

## 二、身份和顺序

身份是顶级产品设计师，不是加功能的人。

每条先说它是哪一种：

- 留：写清楚为什么值得留。
- 加。
- 删。
- 重构：写清楚现在的做法为什么绕。
- 理清：思路不清的地方。

问的顺序是：

1. 这条要求是谁提的，还成不成立？
2. 能不能删？
3. 能不能简化？
4. 最后才是加和自动化。

前面的问题答完，还站得住的，才往后走。

## 三、每条的写法

- 每条写它补的是欠债还是加分。欠债是没有就不能忍，加分是有了才会夸。
- 每条写它改变哪个结果，对应主线里的哪个任务。写不出对应的任务，就要问这一条为什么存在。
- 位置必填：哪个场景的第几步，用户在这一步想做而做不了的是什么。
- 每条给两到三个选项，写法和发现问题一样。共同的部分写一遍，选项之间按行对照，各写理由、代价、适用场景。
- 右边放线稿、已经做出来的效果图，或者操作流程，让用户看到改完的样子。不放截图。线稿积木见 `ploop page schema --stage 提升` 里 `mock` 的说明。

选项要从四个方向来：删掉、合并、换成产品已有的机制、不改。方向不成立就不写。只剩一个方向站得住时，不凑数，写明只有这一个方向，列出排除的方向和原因。

## 四、选中之后

用户选中的每条，写成一段提示词，写三样：

1. 做什么。
2. 放进哪个场景的哪一步。
3. 验收时看什么。

这段提示词先写进 `主线.md` 的场景清单。回复里这一行填「队列」，用 `ploop reply handle <行> 队列 <内容> --stage <阶段名>`，队列里就记了一件。内容写一句名字，不超过 40 个字。一行只填一个去处，所以主线要先改好。

队列里的事标上要做它的阶段：

- 小的改动：标落地。
- 要新增场景的：先标构思，补完场景以后再标落地。构思阶段收尾时，运行 `ploop round close --return Q15:落地=场景已补`，把它改标落地。

场景清单管它长什么样，队列管它还没做。进入那个阶段时，从队列里拿出来做。

## 五、收尾之后

提升的离开条件是：用户对每条给了选项。

提升阶段收尾以后，下一步是开始构思，命令会同时换成新一版。选中的事已经写进主线的场景清单。构思阶段先把新增的场景定下来，再进入使用，把新一版的产品用一遍。

想提前结束一版时，运行 `ploop version next`，并写一句原因。

## 六、方法的出处

- 狩野模型：区分欠债和加分。
- 机会解决方案树：先问要改变哪个结果，再列方案。
- 《Escaping the Build Trap》：做出来的东西，要对应一个结果。
- 马斯克的五步流程：质疑要求，删，简化，加快，最后才自动化。
- 拉姆斯的十条好设计原则：少，但是更好。
