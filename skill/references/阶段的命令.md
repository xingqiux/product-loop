# 阶段的命令

正文只写命令名，用到时的细节写在这里。每条命令的完整用法看 `ploop <命令> --help`。

## 一、开工

第一次在项目里用，先问用户仓库是谁的，再运行 `ploop init --repo 自己的` 或 `--repo 共用的`。

- 同时问用户要不要装会话开始的钩子。同意就加 `--hook 是`。
- 用户后来不想要了，运行 `ploop init --hook 否`。它只撤掉 ploop 写的那一条，别的设置不动。
- 装了钩子，新会话开始时会自动运行 `ploop prime`，把项目的状态和下一步交给你。后端没开时，它写一行怎么启动。

要看这一版做过哪些阶段，运行 `ploop round list`。要看某一个，运行 `ploop round show 落地`。它也写这个阶段收到的回复和每一行的去处，换一个会话接手时先看它。

`ploop --help` 只列日常和按需命令，运行 `ploop --help --all` 才列维护和过渡命令。维护命令管后端、备份、导出和安装，过渡命令只服务旧项目的迁移，2026-12-31 删除。

下面四条会覆盖或删除数据，先问用户，同意了才运行。不要凭 `--help` 自己加 `--yes` 或 `--force`：

| 命令 | 后果 |
| --- | --- |
| `ploop backup restore <快照> --yes` | 用快照覆盖现在的数据。不加 `--yes` 只做预告 |
| `ploop mainline pull --force` | 丢掉 `主线.md` 里没交的改动 |
| `ploop backup gc` | 删掉没有引用、存下超过七天的附件 |
| `ploop export --legacy` | 按旧格式写回项目缓存，供退回旧 skill |

`--json` 给脚本读，AI 读文字输出。加了 `--json` 的命令出错时，错误的 JSON 写到标准输出，退出码照旧，不写到标准错误。

命令找不到时，在产品循环的仓库根目录运行 `pnpm ploop:setup`。本 skill 的目录就是那个仓库里的 `skill/`。

## 二、拿出来的事

`ploop round start <阶段名>` 拿出这个阶段的事。收尾前，每件事要有结果：

- 做完：写在页面某张卡的 `queue` 里，收尾时写 `--done Q12=证据`。
- 不成立：`ploop queue drop Q12 --reason <原因>` 取消。
- 要等别的事：开始时写 `--defer Q9=依赖`，状态变成等待。依赖满足以后，运行 `ploop queue reopen Q9` 改回待办。

落地阶段用 `--take Q12,Q15` 定这一批。不写，就拿出这个阶段全部待办的事。

## 三、等回复

- `ploop reply wait` 默认等 540 秒。到时用户还没提交，退出码是 7，再运行一次。
- 后台运行时写 `--timeout 0`，一直等。
- 退出码 8：等的那一页已撤回，或被新的一页代替。运行 `ploop status`。

### 对话里的回答

用户在对话里直接回答了，这时没有回复可处理。按下面做：

1. 运行 `ploop page withdraw --reason "用户在对话里回答了"`，撤回这一页。
2. 按回答自己处理。产品行为定了，用 `ploop decision add` 记决定。批准了还没做的，用 `ploop queue add` 放进队列，标要做它的阶段。内容不超过 40 个字，细节用 `--note` 写备注，决定的细节写进 `--reason`。改主意的，改 `主线.md`，再运行 `ploop mainline push`。
3. 都处理完，运行 `ploop round close`。

## 四、处理回复

`ploop reply show` 列出回复的每一行，每行写着卡片的标题和行的种类。`ploop reply handle` 给每一行定去处。带图的行，先读 `reply-img/` 里的图，再加 `--read-images`。

一行只填一个去处。一件事要放两处时，填主要的一处，另一处自己补：

- 构思里选了选项：填「决定」。要改主线的，先改好 `主线.md`。
- 提升里选中：填「队列」，`--stage` 写要做它的阶段。卡上列着的事写它的编号，例如 `ploop reply handle 1 队列 Q4 --stage 落地`，编号不变，不另放一件。卡上没有对应的事，才写新事的内容。选中的内容先写进 `主线.md`。
- 决定一项和队列的内容，都不超过 40 个字。超了会被拦下。决定的细节写进原因，队列的细节等放进去以后，用 `ploop queue edit <编号> --note` 补。
- 处理这一行时，命令会把 `主线.md` 的改动交成新的修订。

常见的行和去处：

| 行的种类 | 出现在 | 去处 | 另外要做的 |
| --- | --- | --- | --- |
| 选了选项 | 疑问、发现问题、提升的卡 | 按选的内容：决定、队列或不处理 | 构思填决定，提升填队列 |
| 同意 | 只有一个方向的卡 | 按卡的内容放：决定或队列 | 无 |
| 否决 | 只有一个方向的卡 | 不处理，写原因 | 无 |
| 保留 | 场景清单、设计规范的每一项 | 不处理，原因写保留 | 无 |
| 修改、删除 | 场景清单、设计规范的每一项 | 主线 | 先改好 `主线.md`，说明写改的是哪个部分 |
| 明白 | 先对齐的每个词 | 不处理 | 无 |
| 不明白 | 先对齐的每个词 | 不处理 | 用到它的疑问这一次不算定，下一次换讲法 |
| 只写了备注 | 任何一张卡 | 按备注的意思放 | 无 |
| 想法 | 页面底部的输入框 | 按想法的意思放：要做的填队列，`--stage` 写提升；不做的不处理，写原因 | 无 |
| 取消队列事项 | 队列小卡 | 后端自动改成已取消 | 不用处理 |
| 认可一条更改 | 落地的验收页 | 后端自动记不处理 | 不用处理 |
| 不认可一条更改 | 落地的验收页 | 队列，写那件事的编号 | 收尾时用 `--return` 退回，写原因 |

### 当场做

只有两种：断点，和用户明说现在就改。改完提交，证据写提交号。使用阶段修断点的做法，见「使用代码」。

## 五、收尾

`ploop round close` 检查拿出来的事都有结果。

- 做完的：`--done Q12=证据`，证据写提交号。
- 退回的：`--return Q15=原因`。要改标别的阶段，写成 `--return Q15:构思=原因`。
- 一句话写这个阶段做了什么：`--summary`。
- 想放弃这个阶段：`--abort 原因`，拿出的事都退回待办，不要求给过页。它不和上面几个一起写。给用户看过更改的落地阶段不能放弃，只能逐件收尾。

不用每个阶段都自己收尾。回复处理完、拿出的事都有结果，运行 `ploop round start` 开下一个阶段时，这个阶段自动收尾，输出里写明。使用阶段给出过页的也一样。下面几种要自己运行 `ploop round close`：

- 拿出的事还在进行中，要写 `--done` 或 `--return`。
- 落地阶段：命令另查代码全部提交，更改要用户认可。
- 没给出页，或页被撤回的阶段。有一页在等的，先 `ploop page withdraw`。

收尾时命令按阶段再查离开的条件：
- 构思：主线十个部分至少写好一半，缺得太多拦下，规矩是 think.leave。别的条件靠你判断，见「构思的做法」。
- 使用：覆盖表没有缺口，最近一次运行没有断点，主线的每一步都走到，规矩是 use.leave。
- 落地：见「落地」。

落地阶段收尾前，必须给用户看过至少一页带更改的页，代码要全部提交，回复的每一行都要处理完。提升阶段收尾后，开构思，自动换新版。想提前结束一版，运行 `ploop version next`，写明原因。
