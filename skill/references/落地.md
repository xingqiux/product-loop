# 落地

落地是改产品行为的阶段，规矩最多，拦截也最严。这一份先写落地阶段的流程，再写每条规矩的方法和出处。流程由 `ploop land` 的子命令执行，用法看它们的 `--help`。

## 一、落地阶段的流程

落地固定五步。前四步各留下命令查得到的记录，上一步的记录不在，命令不让进下一步。第五步没有命令查。`ploop land status` 随时看到了哪一步、缺什么。

改动小的走快路，少写几节，少敲几条命令。改动不超过评审界线时，计划写三节就行，重构和评审由命令自己跳过。界线见第四步。超过界线，计划要补全七节，评审不能跳过。

工作区在项目缓存的 `rounds/` 下，`ploop round start 落地` 的输出里给出。下面说的文件都放在工作区里。

| 步骤 | 内容 | 命令 | 记录 |
| --- | --- | --- | --- |
| 一、写计划 | 先读要改的代码，再写计划 | `ploop land plan` | 工作区的 `计划.md` |
| 二、重构 | 先把要改的地方改成容易改的样子 | `ploop land tidy` | 重构的提交和检查记录 |
| 三、功能改动 | 一次一件，先失败后通过 | `ploop land red`、`ploop land green` | 两次运行记录 |
| 四、评审 | 没看过过程的子代理评审 | `ploop land diff`、`ploop land review` | `review.json` |
| 五、重用场景 | 改到的场景重走一遍，出改前改后图 | `ploop use run` | 更改卡里的两张图 |

开始落地前，用 `ploop round start 落地 --take Q12,Q15` 定下这一批。不写 `--take`，就拿出这个阶段全部待办的事。

### 第一步：写计划

计划写七节，`ploop land plan` 查是否齐全。改动小时只写「要做的事」「功能改动」「用什么锁住现有的行为」三节，别的四节不写标题，重构记为跳过；改动超过评审界线，就要补全七节。`ploop round start 落地` 的输出里写了七节的名字：

1. 要做的事。
2. 现状。
3. 要不要先重构：以「要」或「不要」开头。写不要，要给理由，至少六个字。
4. 功能改动：每件写它的名字、对应的队列事项，和检查它的命令。
5. 用什么锁住现有的行为：写检查命令。改产品的提交，要先让使用代码通过，所以把跑使用代码的命令也写在这里。
6. 对应哪个场景。
7. 裁决：一张表，写裁决，理由，错了的代价。

计划的写法抄自几套工程 skill 的共同点。要点：改哪些文件，每一步能单独验证，不留以后再定的空。

没有测试的项目，第一次落地先补一条能锁住现有行为的检查，再改功能。共用的仓库里，「不该变的没变」优先用项目自己的测试。

### 第二步：重构

先把要改的地方改成容易改的样子，例如把几百行的一块拆成几个函数或组件。页面不变，单独提交。然后运行 `ploop land tidy -- <检查命令>`，命令自己跑检查，必须通过。

只改字和样式的小改动，跳过这一步：计划里写「不要」和理由，命令自己记为跳过，不用再运行 `ploop land tidy --skip`。计划只写了三节时，也记为跳过。

重构花的工夫，以这一阶段的一到两成为限。超出了，开一张卡问用户。

### 第三步：功能改动

一次提交一件。每件先写一条改之前会失败的检查，再改。

1. `ploop land red <名字> -- <命令>`：命令自己跑，要失败。
2. 改好，提交。提交说明里写「队列: Q12」，指明这件改动对应的事项。
3. `ploop land green <名字> -- <同一条命令>`：命令自己跑，要通过，提交要在失败之后。

失败和通过的记录，是命令自己跑、自己写的，不收手写的。

### 第四步：评审

改动超过界线时要评审：多于六十行或三个文件，或者改了数据格式、加了依赖。界线的数字在设置里，可以调。AI 也可以主动要求评审。

1. `ploop land diff` 打印这一批改动的差异，前面列出每件改动的检查命令和它查什么。
2. 另开一个没看过过程的子代理，只给它计划和这份差异。
3. 它的意见写进工作区的 `review.json`：每条指到文件和行，分阻塞和建议。阻塞的每条写处置。
4. `ploop land review`。

`ploop land green` 记下最后一件功能改动通过时，改动在界线以内，评审由命令自己跳过，输出里写明改动的规模，不用敲 `ploop land review`。评审的建议当次收口：要么修掉，要么在验收页上写明不修的理由，不再放进队列。

### 第五步：重用场景

这一步没有专门的命令，也没有命令查它。它是改前改后两张图的来源，不能省。漏了改前图，命令不会报错，要自己核对。

1. 改代码之前，用使用代码只跑这一批改到的场景。例：`ploop use run -- node scripts/use/run.mjs S3 S4`。共用的仓库把路径换成 `.product-loop/use-code/run.mjs`。截图在项目缓存的 `use/` 下。
2. 挑出要给用户看的一屏，复制到工作区的 `img/` 下，命名成 `q82-before.png` 这样的名字。
3. 改完并提交以后，把同样的场景再跑一遍。取同一场景、同一步、同一个宽度的图，命名成 `q82-after.png`。不是同一屏，两张图没法对照。
4. 在页面数据的更改区块里，一件改动一张更改卡。`problem` 写之前哪里不对，`fix` 写现在什么样。`before` 和 `after` 写这两张图。新增的东西没有改前图，只写 `after`。
5. 文字的更改不用图，用 `textBefore` 和 `textAfter` 写改前改后的原文，逐行对比由后端算。
6. 使用代码跑不到的界面，用浏览器工具截，仍然是同一步、同一宽度。

### 收尾

- 交出去之前，以设计师的眼光把刚做出来的看一遍。觉得不对的，用 `ploop queue add` 放进队列，内容写一句名字，不超过 40 个字。哪里不对、为什么、是小毛病还是设计问题，写进 `--note`。设计问题标构思。落地的页不出提升卡。
- 运行 `ploop page present`，给用户看更改。收尾前，必须给用户看过至少一页。
- 用户对某条更改点了不认可，这件事不算做完。收尾时用 `--return Q12:落地=<原因>` 退回队列，写了 `--done` 会被拦下。改好再给用户看，用户认可了才能写做完。
- 用 `ploop round close`，做完的事写 `--done Q12=<证据>`，没做完的写 `--return`。收尾前，代码要全部提交。
- 不想做这一批了，运行 `ploop round close --abort <原因>`，拿出的事都退回待办。给用户看过更改以后不能放弃，只能逐件收尾。

## 二、拆步的原因

看过的出处，都把落到代码里这件事拆成至少两步。没有一处是拿着决定直接写。把活交给模型越多，人越接近只顾眼前能跑。所以对策要做进结构里，写一句「注意代码质量」没有用。

## 三、重构和功能改动的分开

出处：Kent Beck 的 Tidy First，和 Martin Fowler 讲预备性重构的文章。意思是：先让这个改动变得容易，这一步可能很难，再去做那个容易的改动。重构和加功能是两顶帽子，一次只戴一顶。

为什么分开提交：

- 重构的时候，行为不该变，所以任何变化都是错。
- 功能改动的时候，行为该变，所以只看该变的那一处。
- 混在一次提交里，变了以后，分不清是哪一种。

官方的代码现代化插件也这样做。保住行为的重构，和重写加等价测试，是两个分开的命令。上一步该留下的文件不存在，下一步的命令拒绝运行。

## 四、证据

六个问题，后面跟着任何能回答它的命令。流程只规定问什么、留什么，不规定用什么工具。

| 问题 | 记录 | 必留或由项目定 |
| --- | --- | --- |
| 该变的变了吗 | 同一条检查先失败后通过的两次运行记录 | 必留 |
| 不该变的没变吗 | 和批准过的结果对比没有差别 | 必留 |
| 评审的阻塞意见都有处置吗 | 评审的意见表 | 必留 |
| 模块之间的依赖方向被打乱了吗 | 查依赖的程序的输出 | 由项目的主线定 |
| 新代码让重复和复杂度变差了吗 | 查重复的程序的输出 | 由项目的主线定 |
| 改的是什么、为什么改 | 提交说明 | 写进提交说明，不单独占一格 |

和批准过的结果对比，来自批准式测试。做法是把批准过的结果和这次跑出来的并排比。它就是改前改后两张图在代码这一面的样子。

证据必须是跑出来的东西，不能是说过的话。所以失败和通过的记录，由命令自己跑、自己写。

## 五、评审

- 由没看过过程的子代理做，因为写的人判断不了自己。只给它计划和改动。
- 通过的标准抄自一家大公司公开的代码评审标准。只要这次改动明确改善了代码整体的健康，就应该通过，哪怕它不完美。没有完美的代码，只有更好的代码。
- 每条意见指到文件和行，分阻塞和建议。指不到具体位置的不收。
- 评审的子代理只读，不动代码。它考虑过、判定为超出这次范围的事，也要列出来，不能悄悄丢掉。
- 它和写代码的是同一个模型，有同样的盲区，所以跑出来的检查结果排在它前面。

## 六、问用户和自己裁决的分界

两头都有出处。一套很有影响的开源工程 skill 主张要裁决，不要停顿。遇到歧义自己决定，把裁决、理由、错了的代价记下来，接着干。因为停下来等人，花掉的是对方一整天。官方的功能开发插件相反：必须先向用户提澄清的问题，再给两三个方案和推荐。

这里分层：

- 用户看得见的行为，和改回来很贵的技术决定，做成卡片问。改回来很贵的，例如数据的格式、新的依赖、目录怎么分。
- 其余的自己裁决，在计划的「裁决」一节记一行，摆在验收页上给用户看。例如函数怎么拆，先改哪个文件，名字怎么起。

判据是两条：用户看不看得见，改回来贵不贵。

## 七、根因

每条落地写根因，一次改一类。改起来别扭，先重构再改，两步分开提交。写根因用五问法：对每个原因再问为什么，问到能动手的那一层。出处：大野耐一的五问法。
