# 使用代码的写法

使用阶段用的是产品本身：平台、软件、插件。使用代码替用户把场景清单里的每个场景从头用到底。它也走一遍面板、宿主、agent、文件和外部服务之间的交接处。边用边截图、量事实，攒成使用记录，也就是使用代码一次运行的结果。

合起来，它就是整个项目的端到端测试和集成测试。它不是只把一条主流程走通的脚本。只走一条路，检查阶段就只能看到那条路上的屏，别处的问题一个都查不到。

## 一、位置和运行

- 自己的仓库：放在 `scripts/use/`，和产品代码一起提交。
- 共用的仓库：放在 `.product-loop/use-code/`，不提交。仓库里不能因为产品循环多出一个字节。覆盖表也在那里，命令会按仓库是谁的去找，不用写 `--coverage`。
- 改产品之前，先在落地计划的「用什么锁住现有的行为」里写上跑使用代码的命令。`ploop land tidy` 会跑它，通过了才算页面没变。

下面以自己的仓库的 `scripts/use/` 为例。共用的仓库换成 `.product-loop/use-code/`，里面的结构一样。

```
scripts/use/
  lib.mjs             连接、截图、量数、点击、等待。Electron 和 Web 各一份，接口一样
  scenarios/
    S1-新建幻灯片.mjs 一个场景一个文件，文件名以主线里的场景编号开头
    S4-从模板开始.mjs
  run.mjs             运行器：不写参数跑全部，写场景编号只跑那几个
  覆盖表.md           页面、入口、操作、状态和交接处，每行写被哪个场景用到
```

运行用 `ploop use run -- node scripts/use/run.mjs`，共用的仓库写 `node .product-loop/use-code/run.mjs`。命令做三件事：

1. 设好环境变量 `PLOOP_USE_OUT`，值是一个空的输出目录。
2. 运行你给的命令。使用代码把结果写成这个目录里的 `use-run.json`，截图也放在这个目录里。
3. 读 `use-run.json`，上传截图，把结果交给后端。

`use-run.json` 不合格式时，命令会拦截。格式的定义，包括每个字段的说明，用 `ploop use schema` 查看。这里只讲怎么用。

## 二、一份最小的使用代码

场景的每一步照抄主线里的一步：做什么，该看到什么。

```js
import { openRun } from "./use-out.mjs";   // 例子在 使用代码例子/use-out.mjs，复制到项目里

const run = openRun();                     // 读 PLOOP_USE_OUT
const scene = run.scene("S1");             // 场景编号写主线里的，不写场景的名字

await scene.step({ step: 1, do: "打开「我的设计」", expect: "看到已有设计的卡片" }, async (ctx) => {
  await page.goto(url);
  await page.getByText("我的设计").click();    // 按用户看得见的文字找元素，不按类名
  await page.getByText("新建设计").waitFor();   // 等不到就抛错，这一步记成断了
  await ctx.screenshot("1400-我的设计", await page.screenshot());
  ctx.facts({ cards: await page.locator(".card").count() });
});

process.exit(run.finish());                // 写 use-run.json；有一步没通过就返回 1
```

写出来的 `use-run.json` 是这样：

```json
{
  "schemaVersion": 1,
  "scenes": [
    {
      "scene": "S1",
      "steps": [
        {
          "step": 1,
          "width": 1400,
          "do": "打开「我的设计」",
          "expect": "看到已有设计的卡片",
          "result": "通过",
          "screenshot": "screens/1400-我的设计.png",
          "facts": { "cards": 12 }
        }
      ]
    }
  ]
}
```

几条要点：

- 场景编号写成 S 加数字，例如 S14。文件名和 `scene` 用同一个编号。
- 按用户看得见的文字找元素，不按类名。用户看不见类名，类名一改，这一步就无故断掉。
- `step` 是主线里这个场景的步号，从 1 数。要看排版的步骤，在几个宽度下各写一项。步号相同，宽度不同。写了截图就要写 `width`。
- `result` 有四种：通过、断了、没走、环境。后三种必须写 `error`，通过的步骤不写。
- 一步里抛出错误，记成断了。同一场景后面的步记成没走。
- 分不清是产品坏了还是环境坏了，记成环境，并写明原因。环境不算产品的断点。
- 截图只收 PNG，路径相对输出目录。
- `facts` 是量到的事实，例如顶栏文字、选项个数、卡片尺寸、文件有没有登记。事实只给 AI 自己看，用来写图注和判断改没改好。不把数字汇总给用户。

`expect` 没出现、动作报错、页面白屏、等超时，都是断点。使用阶段只修断点。写不出 `expect` 的一步，本身就是一条发现，留给检查阶段。使用阶段看到的界面问题也一样，记进队列，标检查。内容不超过 40 个字，细节写备注。

例子里的 `use-out.mjs` 是一个很短的记录器，功能是上面这些。两份连接 Electron 的参考实现用它写结果，见第五节。

## 三、覆盖表

覆盖表是一张 Markdown 表。先从代码和截图里把产品有什么列全，再对照场景。第一列是产品里的一样东西，另有一列名字里带「场景」，写用到它的场景编号。

| 产品里的东西 | 类别 | 尺寸 | 场景 |
| --- | --- | --- | --- |
| 我的设计 | 页面 | 小 | S1、S4 |
| 新建设计 | 入口 | 小 | S1 |
| 生成完文件有没有登记 | 交接处 | 大 | 无 |

也可以不写「场景」这一列，改用 S1、S2 作列名，用到的格子里写任何字。没有一个场景编号的行就是缺口。命令 `ploop use coverage` 列出缺口。

每个类别列什么：

| 类别 | 一行的内容 | 例子 |
| --- | --- | --- |
| 页面 | 每个标签页、每个视图、每个详情页 | 我的设计、模板详情、工作台 |
| 入口 | 每个能点进去的按钮和链接 | 新建设计、使用、返回 |
| 操作 | 点、输、选、筛、拖、返回、拉宽缩窄 | 选「其他」后打字，切筛选看联动 |
| 状态 | 空、加载中、出错、进行中、完成 | 空项目、生成中、宿主崩溃 |
| 交接处 | 面板和宿主、agent、文件、外部服务之间的交接 | 面板关掉重开，状态还在不在 |

尺寸列是可选的，命令不看它。小的是单进程就能跑的。中的要开浏览器或数据库。大的要有 agent 参与或要等几分钟。尺寸说明一个场景慢在哪里、失败了该先怀疑谁。

覆盖表没有缺口，最近一次运行没有断点，才能离开使用阶段。有缺口时，补进最像的场景，或者新开一个场景。新场景先写进主线。一个功能不在任何场景里，先当缺口问用户。用就补场景，不用才写进「不做什么」。默认在使用代码的文件夹里：自己的仓库是 `scripts/use/覆盖表.md`，共用的仓库是 `.product-loop/use-code/覆盖表.md`。放在别处的用 `--coverage <文件>`。

## 四、跑法

- 全跑：`ploop use run -- node scripts/use/run.mjs`。每步的截图和事实收进集中存储。
- 按场景：`ploop use run -- node scripts/use/run.mjs S1 S4`。运行器把场景编号当参数，这是运行器自己的约定，命令不管。修完一处，只重跑改到的场景。
- 按方向：运行器可以再约定一个标签参数，只跑带这个标签的场景。用于就一个方向，在使用和检查之间来回。
- 收尾前全跑一次。使用阶段收尾看的是最近一次运行，只跑了几个场景，别的场景的断点看不出来。
- `ploop use run` 在使用阶段里对照最新的主线：主线写了、这次运行没走到的步，列为缺口，退出码是 1，收尾会被拦下。补场景，或者先改主线。

### 修断点

断点是产品在某一步走不下去。使用阶段当场修，不走落地的五步：不写计划，不要求先失败后通过，不评审。

1. 改前：断了的那次运行已经由 `ploop use run` 收进集中存储，带着断的那一步的截图和当时的提交。不用另外截图。
2. 修产品的代码。只改这一步，不顺手改别的，也不改产品的行为。
3. 改后：重跑改到的场景，这一步通过，就有了改后的记录。收尾前再全跑一次。
4. 提交，说明写场景和步号，例如「修 S3 第 2 步：提交按钮被遮住」。
5. 收尾：没有断点、没有缺口时，`ploop use run` 自己给用户一页只看的使用记录，下一次开始阶段时自动收尾，不用运行 `ploop page present` 和 `ploop round close`。要写收尾说明时，才运行 `ploop round close --summary "修了 S3 第 2 步：提交按钮被遮住"`。

修不了，或者要改产品的行为才能修，停下来问用户。不自己把它标成「环境」，环境只用在确实是环境坏了的步骤上。

`ploop use changed` 列出这一版新出现和变过的屏，检查阶段要看的就是它们。

## 五、连接方式

场景里有 agent 参与的步骤，例如点生成、等 agent 出一份幻灯片。使用代码要真的点，真的等，真的看产物有没有登记，工作台有没有自动打开。不能停在按钮前面。等的时候轮询数据文件和页面文字，不用长 sleep。

Electron（面板在 srcdoc iframe 里）：

- 应用以 `--remote-debugging-port=9222` 启动，`http://127.0.0.1:9222/json/list` 列出所有目标。
- 主窗口是 `type === "page"` 且 url 不含 devtools 的那个。
- 面板 iframe 的目标 url 是 `about:srcdoc`。有好几个时，用脚本的 nonce 去认。先取主窗口里可见 iframe 的 `srcdoc` 里的 nonce。再在每个 `about:srcdoc` 目标里取 `document.querySelector('script')?.nonce`，相等的就是它。
- 截图用主窗口的 `Page.captureScreenshot`，量数在 iframe 目标里用 `Runtime.evaluate`。
- 要宿主认成真实点击时，例如把内容写进对话框再发送，用 `Input.dispatchMouseEvent` 按坐标点，不用 `element.click()`。

Web：把连接部分换成 Playwright 的 `page.goto`、`page.setViewportSize`、`page.evaluate` 和 `page.screenshot`，量数的 JS 原样可用。

`使用代码例子/` 下有四份文件：

- `use-out.mjs`：记录器，把每一步的结果写成 `use-run.json`。
- `use-cdp-screens.mjs`：Electron 加 CDP，多宽度截图、量数、导航探测。
- `use-cdp-probes.mjs`：进表单数输入项，切筛选看联动。
- `dom-diff.mjs`：重构前后逐个同名网页渲染，比较根元素的结构，有一个不同就以失败退出。重构那一步用它核对页面没变。

前三份是一起用的：拆成函数后，每个场景文件调用连接和量数的部分，结果交给记录器。换项目要改的地方，在每份文件开头的注释里写着。

## 六、人工试用

使用代码量不到的地方，由人工试用补上。每次试用按会话记，会话记录写这四项：

- 纲领：一句话，说这次要查什么。
- 时长。
- 发现。
- 遇到的障碍。

会话的记录并进使用记录，检查阶段一起看。

## 七、常见坑

- 面板重装后要关掉再打开一次，不然跑的还是旧版本。先量一个只有新版本才有的元素，确认版本再截图。
- 面板只在打开时才轮询。面板关着时发生的事，例如 agent 写完文件，要靠宿主记住，重开时补做。这类交接处专门放一个场景。
- 缩略图是异步渲染的。一次画几百张卡时要等够久再截，不然全是占位图。等的时候量 `img.naturalWidth`，不为 0 才算出来了。
- 面板会记住上一次停在哪个视图。使用代码开头先回到列表，再开始。
- 截图要裁剪时，`Page.captureScreenshot` 的 clip 在 srcdoc iframe 上不可靠。整张截下来，再用图片库裁。
- 同一个对话里连发两次生成，agent 会把第二次当成改第一份。要新产物就开新会话。
- 依赖外部服务的步骤，例如邮箱、第三方登录，用假服务跑。不然分不清是产品坏了还是外部坏了。
- 无头浏览器里剪贴板、下载、焦点、重绘可能因为环境失败。这类结果记成环境，除非源码里能确认缺陷。

## 八、给检查用的工具

检查推理条件叠加时，需要一样工具：按组件截图，只截那个组件的框，不截整屏。一个状态开头一张、结尾一张。Electron 和 Web 都是先取元素的位置和大小，再按这个框截。它不是使用阶段的规矩，场景代码不用为它改。推理的做法见「检查的做法」。

## 九、方法的出处

使用阶段的做法借了几个成熟的测试方法：

- 测试金字塔（Mike Cohn）：越靠上的测试越贵、越慢、越脆，但每层都要有。使用代码补的是最上面一层，追求覆盖表每行有一条，不追数量。
- 测试奖杯和 Testing Library 原则（Kent C. Dodds）：测试越像用户在用，信心越足。所以按用户看得见的文字找元素。
- 测试尺寸（《Software Engineering at Google》）：按用了什么资源分小、中、大。覆盖表的尺寸列由此来。
- 基于会话的测试管理（James Bach 和 Jonathan Bach）：一次探索有纲领、有时长、有记录。人工试用按会话记，就是这个做法。
- 场景测试（Cem Kaner）：用一个可信、有动机的故事做测试。每个场景对应一份使用代码，要过五条判据，见「构思的做法」。
- 自働化（丰田）：发现异常就立即停下。所以一步断了，同一场景后面的步记成没走，不带着错往下跑。
- 《The Mom Test》：先问用不用、上次什么时候用的，不直接删，也不直接补。覆盖表的缺口这样处理。

更详细的讲解在产品循环仓库的 `docs/依据/`，运行时不用读。
