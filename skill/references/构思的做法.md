# 构思的做法

构思要把产品想清楚，产物是主线。人类团队立项，要拉全组和客户谈两三天。他们不断提、不断删、不断否定、不断问客户，最后才有一份能开工的文档。构思把这两三天压成几次页面往返。

这一份写主线怎么写，和构思阶段怎么走。设计规范的十二个部分各问什么，见「构思反问」。

## 一、主线的位置和修改

- 主线是项目缓存里的 `.product-loop/主线.md`。AI 直接改它。
- `ploop mainline check` 检查主线的十个部分在不在、场景的写法、设计规范的十二个部分。它只检查，不交修订。
- 检查不看内容好不好，内容要按下面的写法自己判断。
- 改完运行 `ploop mainline push`，交成一次新的修订。写数据的命令也会先交有改动的 `主线.md`。
- 别的会话先交了一次修订时，命令会写出 `主线.远端.md`。把它合进 `主线.md`，再运行 `ploop mainline push`。
- 项目里没有主线，先构思。已有主线但缺部分的，只补缺的。
- 用户中途改主意，就改主线。被推翻的决定用 `ploop decision void` 作废，原处留着，不删。只是文字要改，用 `ploop decision edit <编号>`，编号和日期不变。

## 二、主线的十个部分

1. 一句话新闻稿：产品做什么，给谁用，为什么现在存在，承诺什么。它就是定位，界面文案的口气以它为准。
2. 给谁用：每类人一段，只写行为。他们现在怎么做这件事，上次是什么时候，用什么凑合，忍受什么。不写他们会喜欢什么。
3. 要完成的任务：一个任务一行，写四样。情境，要完成的事，现在的凑合办法，忍受的成本。
4. 场景清单：每个任务一到多个场景。写法见下一节。
5. 不做什么和胃口：明确不做的功能和场景，每条写一句原因。胃口是这一版愿意花多少时间，到点没做完的砍。
6. 交付线：客户拿到手第一天必须能做到的几条。每条都能用命令或使用代码验证。写不出验证办法的，还不算交付线。
7. 四个风险：价值、可用、可行、商业，各用一句话回答。答不出的写进待定。
8. 常见问题与待定：写前面几个部分时冒出来的问题。答了的写答案。没答的写成「待定：问谁，什么时候」。
9. 事前验尸：假设一年后这个产品失败了，最可能的三个原因是什么。每个原因配一句现在就能做的对策。
10. 设计规范：按职能把「构思反问」问一遍。十二个部分各占一个三级标题，标题不改字。每个部分的答案是一个值、一条规则或一个例子。这个产品没有的部分，标题照写，内容写「无」和原因。

这些部分的出处：新闻稿和常见问题来自亚马逊的逆向工作法。给谁用来自《The Mom Test》和任务视角。不做什么和胃口来自《Shape Up》。四个风险来自卡根。事前验尸来自克莱因。

## 三、场景清单的写法

场景写成下面的样子。标题是场景编号加名字，新场景可以不写编号，命令收进主线时补上。

```
### S3 导出报表
谁在什么时候用：财务，月底对账时。
1. 在报表页点「导出」 → 看到格式选择，默认是表格文件。
2. 选表格文件，点确定 → 浏览器开始下载，页面提示已导出。
```

每个场景过五条判据：

1. 有动机：写明当事人为什么要做这件事。
2. 有说服力：这里失败了，有话语权的人会要求修。
3. 可信：现实里真的可能发生。
4. 够复杂：牵涉多个功能，或者复杂的数据和环境。
5. 结果能判定：越复杂越容易把错误结果当成正常，所以要写清楚成功是什么样。

场景里写用户看得见的行为，不写实现。一个功能不在任何场景里，不等于没人用。那是覆盖表的缺口，使用阶段先问用户用不用。

## 四、构思阶段的流程

构思阶段内部固定六步，只往前走。后面发现前面错了，也不回头重谈。砍掉的候选不捡回来，新发现的事进队列，等下一次构思。

1. 问句：把要定的事写成一个能回答的问句。
2. 调研：先定胃口，分三档。见第五节。
3. 先对齐：这一页的选项会用到的新词和新做法，先摆在疑问前面。见第六节。
4. 候选和草稿：每个要定的事出两个候选。设计类的要画草稿，见第八节。
5. 工程师过一遍：见第九节。
6. 用户定。

每个阶段要定哪几个部分，不固定，按下面的顺序：

- 构思阶段第一次：定一句话新闻稿、给谁用、要完成的任务。
- 第二次：按任务出场景清单的草稿，再定不做什么和胃口。用户在每个场景上点保留、修改或删除。
- 第三次：出交付线、四个风险、事前验尸和待定，用户回答待定。

哪个部分用户没有确认，就再来一次。场景清单和设计规范的草稿，写进各自的区块。整段写进疑问卡的文字，会被拦截。

离开构思的条件。第 1 条命令会查：收尾时主线十个部分至少写好一半，缺得太多拦下，规矩是 think.leave。后面三条靠你判断，用户点头才收尾：

1. 主线的十个部分都有。
2. 待定里没有卡住某个场景的问题。
3. 每个场景过了五条判据。
4. 每个部分用户都确认过。

## 五、调研的三档

带着外面参考的疑问卡，在页面数据里写 `research`，先定档再去查。

- 不查：写 `reason`，说明为什么不用查。
- 快查：AI 自己定方向，看两三处，不用先问用户。
- 深查：先把问句和检索计划给用户批，批了再查，`approved` 写是哪个阶段批的。开始前分好每个代理能搜多少次。广搜之后，收三四条深看。另一个代理核对引用。看过没有用上的，连同理由一起交给用户。

查到的资料写进页面的参考区块，只给人看，不用点。

## 六、先对齐

问用户明不明白，人多半会答明白。所以先把新词摆出来，让用户用自己的话说一遍。

- 每个新词一张小卡，写五样：
  - 名称。
  - 用在哪张疑问卡。
  - 一句话的意思。
  - 这个项目里的一件真事。
  - 必要时一张图。
- 用户对每个词点明白或不明白，旁边有一个可以不填的输入框，用户用自己的话说一遍。写了的，下一次回答对不对。
- 有一个词点了不明白，用到它的疑问卡这一次不算定，下一次换一种讲法。
- 用户只点了明白、没有写的，疑问卡里照样用大白话。
- 新词首次出现时在这里解释一次，全篇只用这一个词。

## 七、候选和追问的写法

- 每次对要定的每件事出两个候选，写成疑问。候选就叫候选，不分颜色。
- 几个候选共同的部分写一遍，配图。候选之间只写差别，按行对照，再各写理由、代价、适用场景。
- AI 在下面写自己的看法，固定两行。每条最多三句，不重复，不催。
- 追问只问已经发生的事：上次是什么时候，怎么处理的，花了多少时间。不问「你会不会用」和「你觉得好不好」。追问没有选项，只有备注框，来源写看了哪个文件、哪句话才问的。

AI 要有自己的看法并守住。用户不同意时，先看用户给的是事实还是意见。

- 是事实，例如上次怎么做、花了多少时间：改主张，并说明为什么改。
- 是意见：把理由再讲一遍，仍然让用户定。

用户定了，就记进决定，之后不再翻出来。决定一项不超过 40 个字，细节写进原因。处理回复时，选了选项的这一行填「决定」，要改主线的先改好 `主线.md`。

构思和检查是两个角色，倾向相反。构思倾向提出主张并守住。检查倾向只对定义给小意见，真有理由才给。这只是倾向，不是页面上的标签。

## 八、设计类的疑问

长什么样、怎么摆、什么气质，这类疑问在数据里标 `design: true`。一张卡分三层，顺序是先看，再画，再谈：

1. 先看：去看外面两三个已有的产品或设计。截图放进来源，标 `outside: true`，各写一句它怎么解决同一个问题。候选从看到的东西里来，不从脑子里来。
2. 再画：每个候选一份草稿，用线稿积木或一张草稿图，写项目里的真文字。要的是粗的、快的草稿。文字说不清，线框图又太细。
3. 再谈：写我的看法，用户在草稿上点评。不满意就再来一次改草稿，不动真界面。

问题大到整页重来时，先用一次只谈方向，再画。

草稿要对着设计规范画。有设计类疑问的那一页，要同时带上设计规范区块。区块里列出这个新组件用到的规范，例如状态、字段名、文案、颜色。已有的原样摆出来，没有的先补成一格，让用户点保留、修改或删除。缺了会被拦截。

原因：《Shape Up》把想清楚和动手做分成两条轨，没想清楚的事不排进动手做的那条轨。所以选项里没想清楚的地方写在代价里，定了以后进队列，标构思，不带进落地里猜。

## 九、工程师过一遍

用户选之前，AI 先以工程师的身份，把每个候选过一遍：

- 看代码现状，写每个候选在这个胃口里能做到什么，坑在哪里。
- 可以提新的候选。
- 拿不准的，做一次限时的试验，到点就停。
- 不否决。有异议，记进决定，写「有异议，照做」和错了的代价。
- 不涉及代码的问题，写一句「不涉及代码」，跳过。

原因：绕圈子的根因是工程师介入太晚，一棒接一棒地传。一开始花几个小时让工程师参与，能省掉后面几周。工程师不只是判断可不可行的人，也是提方案的人。问法从这件事能不能做，换成这件事在这个胃口里能不能做：时间固定，能变的是范围。
