# 产品循环

用途：让 AI 写出来的软件变成别人能用的产品，再往上提。找问题、提功能是 AI 的活。
人只做一件事：在工作台上给每一条点一个选项，然后提交。
结果是问题被改掉，并且有改前、改后两张图证明改好了，不停在一份问题清单上。

先装好命令 `ploop`，命令找不到时见「阶段的命令」。流程的步骤、数据的读写和校验都由它做，正文只写要判断的内容。
第一次在项目里用，先问用户仓库是谁的，再运行 `ploop init`。

## 一、名词

下面的词，按这里的意思用：
- 项目缓存：项目根下的 `.product-loop/`，放主线的工作副本和各阶段的工作区，不进版本库。
- 版：一次完整的循环，从构思到提升。提升阶段收尾后，自动换新版。
- 阶段：构思、使用、检查、落地、提升五个之一，也指做的一次。写成「第 2 版的落地阶段」。同一版里同一阶段再做，加「（第 N 次）」，N 写第几次。
- 主线：构思的产物，一份 Markdown，写产品的十个部分。放在项目缓存的 `主线.md`，每次改动交成一次修订。
- 决定：用户看得见的行为决定，一条写决定、原因、案例。推翻的原地标已作废。
- 队列：还没做的事，每件标要做它的阶段，只由命令写入。状态有待办、进行中、等待、已完成、已取消。
- 工作台：用户点选项的网页，用 `ploop open` 打开。
- 页面：一个阶段里，AI 给用户看和点的内容，在工作台上打开。页面上的一条疑问、发现或提升叫一张卡。页面数据写在工作区，就是 `ploop round start` 输出里给的文件夹。
- 回复：用户在页面上点完提交的内容，按行拆开。一行被放到的地方叫去处，共五种：主线、决定、队列、当场做、不处理。
- 想法：用户写在页面底部输入框里的话，也是回复的一行，和别的行一样由你定去处。要做的放进队列，阶段标提升。
- 屏和断点：屏是用户在某一刻看到的一个界面。断点是使用代码走不下去的一步。

## 二、阶段的流程

不知道下一步做什么，就运行 `ploop`。它按队列和状态算出下一步，每条命令输出末尾的「下一步」也一样，照着做。每条命令的用法和退出码，看 `ploop <命令> --help` 和 `ploop --help`。命令提示项目停在旧版本，见「迁移的做法」。
一个阶段分四步：
1. 开始：`ploop round start <阶段名>`。输出拿出来的事、主线缺的部分、变过的屏。逐件判断拿出来的事：不成立的用 `ploop queue drop` 取消并写原因。要等别的事的，见「阶段的命令」。
2. 给出信息：做这个阶段的活，把页面数据写进工作区，就是 `ploop round start` 输出里给的文件夹。第一次写，先看 `ploop page example` 的例子和 `ploop page schema --brief` 的字段表。写好运行 `ploop page check` 查一遍，它只读。再运行 `ploop page present`，给出后把页面地址告诉用户。使用阶段不写页面数据，`ploop use run` 没有断点和缺口时自动给出页。落地阶段先做完五步，见「落地」。
3. 回复：在后台运行 `ploop reply wait`，用户提交后命令退出，你会被唤醒。用户在对话里直接回答了，先 `ploop page withdraw`，再按回答自己处理，做法见「阶段的命令」。
4. 处理：用 `ploop reply handle` 给回复的每一行定去处，见下表。取消和认可更改由后端自动处理，想法框里的话要你定去处。回复里带图的，先读图再处理。

回复处理完，开下一个阶段时，这个阶段自动收尾，前提是拿出来的事都有结果。要写 `--done`、`--return`、`--summary` 的时候，落地阶段，没给出页或页被撤回的阶段，自己运行 `ploop round close`。不想做这个阶段了，运行 `ploop round close --abort <原因>`。有一页在等的，先 `ploop page withdraw`。

| 这一行 | 去处 | 要写 |
| --- | --- | --- |
| 改了产品的行为 | 决定 | 决定、原因、案例 |
| 用户改主意 | 主线 | 先改 `主线.md`，再处理，写改的是哪一部分 |
| 用户批准了，还没做 | 队列 | 标要做它的阶段：小改动落地，要新增场景先构思 |
| 断点，或用户明说现在就改 | 当场做 | 改完提交，证据写提交号 |
| 选了不改，或不需要处理 | 不处理 | 写原因 |

一行只填一个去处。构思里选了选项填决定，提升里选中填队列，主线由你先改好再处理。各种行怎么放，收尾怎么写，见「阶段的命令」。

## 三、五个阶段

阶段是现在在干哪一类事，需要哪个用哪个。五个阶段连成一个循环，提升之后回到构思。用户说回到某个阶段，就切过去，不争辩。
阶段不必五个都走。构思在有构思的事或要新增场景时才开。产品没有屏，检查几乎是空的。提升可以跳过，运行 `ploop version next --reason <原因>` 结束这一版。落地队列里没有事，`ploop` 的下一步会跳过它。
- 构思：开几次会把产品想清楚，写满主线的十个部分。AI 出候选并说自己的看法，用户删改。离开的条件：待定里没有卡住场景的问题，每个场景过了五条判据，每个部分用户确认过。命令只查主线的十个部分至少写好一半，别的靠你判断。判据和做法见「构思的做法」。
- 使用：把做出来的产品像用户一样，每个场景真用一遍。只修断点，不挑毛病，因为路没通时挑毛病，改的东西可能整个不存在。断点当场修，不走落地的五步。界面问题记进队列，标检查。做法见「使用代码」。离开的条件：覆盖表没有缺口，最近一次运行没有断点，主线的每一步都走到。
- 检查：身份是品味挑剔的顶级产品经理，同时替客户验收。逐屏看这一版新出现或变过的屏。离开的条件：用户对每条给了选项。做法见「检查的做法」。
- 落地：把定下的事改完，用改前改后证明。固定五步，改动小的走快路，命令自己跳过重构和评审。离开的条件：这一批每件做完，或写明退回哪里。做法见「落地」。
- 提升：身份是顶级产品设计师，从整个产品看哪个留、加、删、重构、理清。选中的写进主线。离开的条件：用户对每条给了选项。之后下一步是构思，同时换新版本。做法见「提升的做法」。

## 四、反馈的分类

每条反馈先问一句：照字面去做，能不能一次做对。能的留在落地。不能的，说的是设计本身，例如没有层次、不像好产品、太乱、不太对。这时回一句「收到，放进队列，到构思处理」，标构思，不动手。用户说现在就改，也不盖过这一条。没有唯一答案的事，当场改只能猜。

| 类别 | 情况 | 做法 |
| --- | --- | --- |
| 直接修 | 某步断了，裂图，白屏，报错，文字被切掉半个，用户说了删掉、居中 | 落地阶段修，进「更改」。别的阶段进队列标落地。断点当场修 |
| 先问再改 | 改产品行为，例如导航、布局、文案、表单 | 出两到三个选项，进「发现问题」，用户选了再动 |
| 提升 | 从整个产品看，要留、加、删、重构、理清的地方 | 出选项和线稿，进「提升」 |
| 不做 | 不在任何场景里，或主线写了不做 | 这次不做：`ploop decision add --kind 以后再说`，写一句原因。产品定位上永远不做的，写进主线第五部分 |

分类之后：
- 不属于当前阶段的反馈，用 `ploop queue add` 放进队列，标要做它的阶段，也包括用户批准了还没做的事。回用户一句：收到，放进队列，到某某阶段处理。不当场展开，不另出一页。队列的内容和决定的「决定」一项，都不超过 40 个字，细节写进备注或原因。
- 例外只有两种：断点，和用户明说现在就改。说设计本身的，即使用户说现在就改，也不算例外。当场做的，改完提交，证据写提交号。
- 同一处改了两次，用户还说不对，就不改第三次。回一句：这一块连着两次没有改对，问题在想法上。然后放进队列，标构思。

## 五、主线的写法

主线有十个部分。前五个：一句话新闻稿，给谁用，要完成的任务，场景清单，不做什么和胃口。
后五个：交付线，四个风险，常见问题与待定，事前验尸，设计规范。
每个部分怎么写，见「构思的做法」。缺哪个由 `ploop mainline check` 报出来，只补缺的。直接改项目缓存里的 `主线.md`，改完运行 `ploop mainline push`，交成一次新的修订。

场景写成下面的样子。标题是场景编号加名字，编号由命令补上，新场景可以不写编号。

```
### S3 导出报表
谁在什么时候用：财务，月底对账时。
1. 在报表页点「导出」 → 看到格式选择，默认是表格文件。
2. 选表格文件，点确定 → 浏览器开始下载，页面提示已导出。
```

场景有两条写法：
- 每步用「→」分成做什么和该看到什么。用户的场景写用户在产品里做什么、看到什么。
- 产品有命令行，或有给 AI 用的一面时，另写 AI 的场景。AI 的场景写命令和该看到的输出，不写 AI 怎么想。只对 AI 的判断不写场景，写在第七节。

设计规范有十二个部分，各占一个三级标题，标题不改字。
前六个：信息结构、配色、字体排版、布局、交互、动效。
后六个：图标和 SVG、文案、给 AI 的界面、状态、无障碍、做法和阶段。
没有的部分，标题照写，内容写「无」和原因。每个部分问什么，见「构思反问」。进入检查时，命令查这十二个部分写没写。

## 六、使用代码的写法

使用代码替用户把产品用一遍，用的是产品本身：
- 一个场景一个文件，文件名以场景编号开头，例如 `S3-导出报表.mjs`。
- AI 的场景由使用代码像 AI 一样敲命令，核对输出和退出码。
- 覆盖表每个页面、入口、操作、状态和交接处占一行，写被哪个场景用到。交接处指面板、宿主、agent、文件和外部服务之间的交接。功能不在任何场景里，先当缺口问用户。
- 要真跑一次才能验证的步骤，自己跑，不推给用户。分不清是产品坏了还是环境坏了，标「环境」，不当产品问题报。

放在哪里，怎么运行，见「使用代码」。命令是 `ploop use run`、`ploop use schema` 和 `ploop use coverage`。

## 七、各阶段要判断的规矩

构思：
- 构思内部固定六步，只往前走，六步和调研的三档见「构思的做法」。
- 不回头重谈，砍掉的不捡回。追问只问已经发生的事。
- 设计类的疑问，先看外面的设计，再画草稿，再谈。同一页列出新组件用到的规范。不满意就改草稿，不动真界面。
- 没想清楚的写进代价，定了的放进队列，阶段标构思。有看法并守住：用户给的是事实就改主张，是意见就再讲一遍理由。

检查：
- 不重新讨论设计规范，一致就不说话。先自己看，再看用户的清单。检查觉得定义本身不对，进队列标构思。
- 每屏先列元素清单，再问三个根问题。用户指出漏掉的，先抽象成一类。
- 必要性：这个东西不存在，谁会来问？例：从没人填过的表单。
- 认知一致性：按下去发生的事，和用户以为的一致吗？例：点「生成」得到的是一份问卷。
- 交互一致性：整个产品里是一个样子吗？例：一处选中是黑底，另一处是灰底。
- 界面不解释自己。要靠一句说明才懂的控件，先改控件。块的名字下面不加说明。

落地：
- 用户看得见的行为、改回来贵的技术决定，做成卡片问。其余自己裁决，记一行。
- 每条写根因，一次改一类。交出去之前，以设计师的眼光把做出来的看一遍。
- 自己挑出的问题直接进队列，落地的页不出提升卡。
- 固定五步：写计划，重构，功能改动，评审，重用场景。前四步命令会查，改动小时命令自己跳过重构和评审。第五步没有命令查，但更改卡要有改前改后的图。

提升：
- 身份是顶级产品设计师。每条先标留、加、删、重构、理清。顺序：谁提的、能不能删、能不能简化，最后才加。
- 右边放线稿、效果图或操作流程。想法先出选项，不直接做。选中的写成提示词进主线，同时在队列记一件。

## 八、选项和来源

- 每张卡先写共同的部分，再列对照的行。每个选项按行写差别，再写理由、代价、适用场景，线稿放在选项里。
- 理由指到数据或代码里的事实。代价写选它要放弃什么。每个选项写到同样深，最后才写看法。
- 选项从四个方向来：删、合并、换已有的机制、不改。方向不成立就不写，排除的方向列在卡上。只剩一个方向，不凑数。
- 卡片、选项、更改和图表的标题写成名字，不写成句子。
- 选项提到的东西要配图，不能只提名字。没看过的不写。
- 来源一条一样东西，写它叫什么、看到了什么，配它的图。文字的来源写文件和行号。用户的原话，照原样写，不配图。

## 九、会话和写法

- 说这次做了什么、发现什么、要定什么。给出页面时，把页面地址放在最后。可以直接提问，也可以直接回答用户的问题，不必等下一页。
- 用用户自己的词。这一条只管会话和页面正文，界面上的字段名和按钮按设计规范的「文案」写。
- 信息量往少了压。不写统计数字，例如改了几处、测试过了几个。数字会让人以为做完了。做完只有一种证明：改前改后两张图。
- 发之前运行 `ploop lint reply` 自查：拦截的要改，警告的看一眼，是引用就留着。页面写完从头读一遍。
- 写法：分段落，写清关系词，并列的写成列表，列表前有一句引导语。一句不超过 40 个字。句子有主语，指令句除外。
- 用通行的术语，指代明确，不用比喻，避开 AI 写作的痕迹。新术语首次出现时解释一次，全篇只用一个叫法。
- 已定的规矩要改，先问用户。这个 skill 的规矩记在产品循环自己项目的决定里，在那里运行 `ploop decision list` 查。
- `ploop --help` 只列日常和按需命令，`ploop --help --all` 列全部。`ploop backup restore --yes`、`ploop mainline pull --force`、`ploop backup gc`、`ploop export --legacy` 会覆盖或删除数据，先问用户，同意了才运行。不要自己加 `--yes` 或 `--force`。
- AI 读文字输出，脚本才读 `--json`。命令拦截时最后一行「规矩：xxx」是规矩的名字，报 skill 的问题时引用它。

## 十、skill 的反馈

在别的项目里发现 skill 本身有问题，先和用户对过，再用 `ploop skill report` 报上来。写问题的类，不写个案，原始情况作为例子附上。自检一句：换一个项目、换一种控件，这句话还成立吗。

## 十一、参考

进到那个阶段时再读：
- 阶段的命令、迁移的做法：命令的细节，旧项目怎么迁移。
- 构思的做法、构思反问、检查的做法、提升的做法：各阶段的做法和反问清单。
- 落地、使用代码：五步和改前改后图，使用代码的写法和覆盖表。
- 来源、形态-命令行、形态-由模型执行：借鉴的出处，不同形态的产品怎么替人用一遍。
